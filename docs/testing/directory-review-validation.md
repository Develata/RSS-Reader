## 回归与修复

在所有文章页、全部已读状态下，先收起当前组并打开其他组，再标记一篇文章为已读。来源未读数完成刷新后，首次实现会因整个 presenter 的 `Arc` 改变而重置目录手动状态。Web 时间/来源两种分组及可见 Windows WebView2 均已复现。它是实际状态回归，与 PR19 原始四项旧契约键盘失败分开记录。

修复将目录重置身份收窄到页面、初始路径和目录结构；原有查询/分组上下文仍参与重置。来源摘要等无关元数据变化不重置 manual/open 状态。顶部和侧边目录继续独立订阅同一 Rust 状态，文章 presenter 不接收目录交互状态，没有 application/domain/infra 或存储变更。

新的等待入口只等待已观测的 bridge 消息、导航及挂载消费者提交，不能证明未来 I/O 或平滑滚动已完成。测试先等待真实标记与来源未读数更新，再使用该入口验证整个展开集合和三个滚动位置；不能以三次 rAF 未变化代替原生异步提交完成。

## 性能方法与边界

[首次比较](./directory-follow-validation.md)的监听阶段/先后顺序和 rAF 条件轮询会混入系统性偏差；Web 的构建来源也不一致。原始数据保留，原“一帧收益”和“未退化”结论撤回，本轮不把旧工具数值拼入新样本。

两版均在同一 Windows 主机使用 Rust 1.98.1、dx 0.7.10、锁定 Dioxus 0.7.9 和相同 release 参数。dx 仍报告版本差异，构建成功；没有把它隐去或通过升级依赖改变范围。A 从 `9815d4e8` 的只读 Git archive 在 E 盘构建；相对生产基线 `e8c6ee1` 的 crate 差异仅在 `cfg(test)`，不进入 release。没有创建 C 盘 worktree、切换当前分支或改写旧基线目录。

Web 使用隔离 headless Chrome，1280×800、DPR 1；原生使用独立 SQLite/profile 的可见聚焦 WebView2 窗口，1280×900、DPR 1.5。每宿主串行 A1、A2、A3、B1、B2、A4：先 A/A，再 A/B、B/A。每路径每批预热 3 次，保留 100 个样本。四组小样本试采另存，不纳入正式比较。采样期间不并行编译、测试或其他 GUI 自动化；普通 OS 后台活动未控制。

计时统一从可信浏览器输入的 `event.timeStamp` 起算，窗口捕获监听和 MutationObserver 均先于动作安装。完成条件由 DOM 变更、滚动/事件微任务检查，另报此后两次 rAF 的代理时间，不用 rAF 轮询决定 DOM 起止。记录监听延迟，核对时间戳时钟域、可信标记和可见/聚焦状态。它不包含硬件/OS 输入延迟，也不等于真实显示延迟。

共同路径包含同一已展开组内的真实 wheel 高亮变化、非活动组的鼠标/Enter/Space 展开，以及同页点击后目标/hash 对齐。预先统一其他组折叠、主列表几何和导航 hash；特别是每次导航均采用相同 hash 前提，避免首轮与后续轮走不同滚动分支。

新版另测从当前组手动关闭、其他组展开状态，经真实主列表 wheel 恢复跟随：分别保持同组或跨入另一组，验证实际位移、活动目标与只展开当前路径。旧版没有等价的 manual→follow 契约，因此这两条只报告 B 的实测时延，不伪造 A/B 收益。fixture 中目录路径可能已在可视区，该测量不能代表所有远距离目录对齐。

每个独立批次分别报告 DOM 和代理时间的中位数及 nearest-rank p95，保留全部正式样本。A/A 的中位数/p95 差是当日噪声观测，不是可接受退化的预算；比较分别使用 B1−A3 与 B2−A4，不靠合并中位数覆盖批间差异。100 个样本的 p95 仍只有少数尾部观测，属于描述性统计，不是置信界限。

## 正式结果

两宿主各完成 6 批、3400 个正式样本，合计 6800；所有正式批次的可信输入、可见/聚焦条件和 console / ignored console error 检查通过。该总数不用于代替每路径每批 100 个样本的尾部证据。以下 A/B 比较是旧方案与完整 Rust 候选的比较，不能归因于本轮元数据重置修复这一处改动。

**没有证实整体性能不退化，且观察到小幅 DOM 代价：**

- Web 滚动高亮 DOM 中位数：B1−A3 **+1.15ms**，B2−A4 **+0.95ms**；p95 分别 +1.00 / +3.00ms。A/A 中位数差 0.15ms，四批 A 中位数跨度 0.45ms，这个中位数差不能直接抹为零。两帧代理中位数 +0.70 / +1.50ms，p95 +5.90 / +10.10ms；四批 A 的代理 p95 本身跨度 9.30ms，尾部解释须保留这种波动。
- Windows 滚动高亮 DOM 中位数 **+1.50 / +1.30ms**，p95 **+1.60 / +1.50ms**；四批 A 在记录精度下接近相同。代理中位数和 p95 却都约 −0.10ms，说明只看两帧代理会隐藏 DOM 代价，不能据此宣称没有退化。
- Windows Space 展开 DOM 中位数 +0.80 / +0.20ms，p95 +1.30 / +0.50ms；四批 A 中位数/p95 跨度为 0.60 / 0.90ms。其余展开动作接近基线。保留这些小幅差异，不将它们笼统归零。
- Windows 导航 DOM 中位数 −5.15 / −4.50ms，代理中位数 −5.20 / −4.55ms；它包含实际平滑滚动，未隔离 controller、IPC、layout 或显示成本。Web 导航中位数 +0.50 / +0.40ms，小于 A/A 的 2.65ms 波动；A 的 p95 跨度达 97.90ms，不能由单个尾部差值推出稳定收益。
- 新版恢复跟随 DOM 中位数：Web 同组 50.20 / 50.45ms、跨组 50.40 / 50.50ms；Windows 同组 19.70 / 19.80ms、跨组 20.10 / 20.10ms。逐批 p95 及代理值见下表。它们是 B 的绝对测量，不是相对旧版的优化量。

这些是固定 fixture、两批候选与四批基线的描述性结果；没有预先约定性能差异预算或统计置信界限，不将交互通过等同于性能目标全部达成。PR 保持 Draft，性能与内存目标仍单独验收。

## 未测量与限制

没有物理显示时延、掉帧、独立 layout 成本、冷启动/卸载后首次展开、完整进程树或存活 Rust 内存测量。本轮不复用旧快照声称内存下降。仍保留折叠 DOM；CSS 折叠不能证明省内存。

未完成 Android 原生 GUI、真实触控板/触屏惯性、全平台滚动条及辅助技术验收。响应式 Web 和 Android CI 构建不能替代这些场景。后续若考虑卸载节点，须另外检查首次展开、恢复跟随、焦点及滚动稳定性。
