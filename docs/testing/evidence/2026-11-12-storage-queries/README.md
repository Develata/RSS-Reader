# 文章列表、计数与订阅摘要的查询计划证据

日期：2026-11-12。基线 `origin/main` = `7d60a59c`（资料库 schema 与 v0.2.3 相同）；改动见分支 `claude/storage-linear-queries` 与[交接](../../../handoffs/2026-11-12-storage-linear-queries.md)。

## 结论

原先三类查询都要逐行读全部文章，并且每次加载都会执行：未限订阅的文章列表（要把所有文章排完序再取一页），列表旁的归档计数，以及订阅页的未读数和总数。

改动后：

- **列表**沿排序索引按列表顺序读，凑满一页就停，不再排序。匹配很少时仍要扫完整个索引，耗时与原先相当（见“最坏情况”）。
- **计数和订阅摘要**只读新的覆盖索引，不再读文章行。工作量仍随文章数线性增长，但每篇只读索引里的几十字节。

在 25 万篇文章的库上：

- 默认首页列表从 34.6 ms 降到 3.2 ms。
- 归档计数从 195.1 ms 降到 8.0 ms。
- 订阅摘要从 199.4 ms 降到 8.2 ms。

全部 270 种列表形状与 270 种计数形状，两版返回的结果完全相同。计划变化后仍然变慢的有 9 种，增幅都在 6 ms 以内，见“退化”。

## 方法

- **夹具**：[make_fixture.py](./make_fixture.py) 用仓库迁移 0001、0002 建库。
  - 规模：200 个订阅（5 个已删除），5 万或 25 万篇文章。
  - 行宽：标题、URL、作者和约 400 字摘要按真实行宽填充。
  - 分布：10% 未读、2% 收藏、3% 手动归档、5% 无发布时间，发布时间跨约 6 年。
  - 与应用一致，不跑 `ANALYZE`。
- **带索引的副本**：复制夹具后执行下面的语句，定义与迁移 0003 的 `idx_entries_feed_flags` 相同：

  ```sql
  CREATE INDEX cand_w ON entries(feed_id, is_read, is_starred, is_archived, published_at)
  ```

- **对比**：[final.py](./final.py) 把 `store/entries.rs`、`store/feeds.rs` 的 SQL 原样拼出两版（当前 main 与本改动）。
  - 覆盖读 × 收藏 × 归档 × 范围 × 标题搜索的全部组合。范围分全部订阅、单订阅和 29 个订阅（脚本取 `range(3, 200, 7)`）。
  - 列表都带 `LIMIT 2001`。
  - 每个形状两版交替运行 5 次取最小值，并断言两版结果完全相同。
  - `listed_title` 用 Python 截断函数代替。
  - 原始输出：[final-output.txt](./final-output.txt)。
- **环境**：Python 3.13 自带的 SQLite 3.53.1；应用捆绑的是 3.53.2。
  - `store::query_plans` 单元测试在捆绑版本上确认了本文依赖的计划。
  - Pages 演示链接 sqlite-wasm 3.53.0，在那里既没有计时，也没有核对计划。
  - 5 次取最小值只说明可重复的下限，不代表延迟分布。

## 最坏情况：没有匹配的列表

脚本：[nomatch.py](./nomatch.py)，输出：[nomatch-250k.txt](./nomatch-250k.txt)。

测法：给 25 万篇的副本补齐发布时间，再把归档分界设在所有文章之后，相当于全部文章都已自动归档。

| 查询 | 原先 | 改动后 |
| --- | --- | --- |
| 默认首页列表（结果为 0 篇） | 195.3 ms | 191.7 ms |
| 同一状态下的计数 | 193.0 ms | 7.8 ms |

列表要沿排序索引逐篇查看行，才能确认不匹配，所以只免去了排序。这种状态出现在订阅源都已停更、所有文章都超过归档期限时。要改善它，需要能按发布时间划定范围的写法或更宽的排序索引，已列为后续事项，本次不做。

## 退化

做法：对 25 万篇时第一轮慢于 1 ms 的形状逐个复测并比较计划。脚本：[recheck.py](./recheck.py)，输出：[recheck-slower-250k.txt](./recheck-slower-250k.txt)。

**计划变了、复测仍慢**的有 9 种：

- **列表 2 种**：未限订阅的标题搜索。只看手动归档时 189.0 → 192.4 ms，隐藏自动归档时 194.3 → 198.0 ms，约 +2%。
- **计数 7 种**，主要是“只看收藏”的计数：
  - 原因：原先走收藏索引，只读 2% 的行；现在逐个订阅扫描覆盖索引。
  - 例子：隐藏自动归档时 0.4 → 4.2 ms，加搜索时 3.9 → 9.5 ms。
  - 另一种是“不看收藏 + 搜索”，24.6 → 27.9 ms。
  - 最大绝对增量 5.9 ms；同一改动让默认归档计数省下约 187 ms。
  - 收藏越少，这一相对代价越明显：独立评审在 10 篇收藏的库上测得约 0.002 → 3.4 ms。

**计划没变**的差值，多数在复测中消失。仍有几种复测后约慢 1–2 ms（约 177 ms 中的 1%），例如单订阅 + 已读 + 收藏 + 只看手动归档 176.1 → 177.6 ms。计划相同不能证明执行成本相同，这些残差未定性，可能来自多一个索引后的文件布局或缓存差异。

另有一个“单订阅 + 已读 + 收藏 + 搜索”列表，首轮记为 +25.6 ms。两版计划相同，复测 9 次的中位数分别为 185.5 和 186.3 ms。

## 选择过程中排除的写法

- **所有语句都从 `entries` 出发**：多订阅范围的列表在 25 万篇时慢 24–33 ms，而且已读筛选的计数仍要读行，约 175 ms。
- **只加索引，`OnlyArchived` 仍写成 `OR`**：规划器把它拆成多索引并集，已读或未读 + 不看收藏 + 多订阅的归档视图慢 30–50 ms。改写成 `ExcludeArchived` 的否定后，这种计划不再出现。
- **只加 `(feed_id, is_read)`**：未限订阅的默认列表会改用这个索引，慢到 39 ms。

## 代价

脚本：[collateral.py](./collateral.py)，本次输出：[collateral-250k.txt](./collateral-250k.txt)。

- **写入**（25 万篇）：
  - 测法：语句在事务内执行后回滚，只计语句本身的执行时间，不含提交、fsync 和 WAL 检查点。
  - 附件那次运行：刷新式 upsert 120 行 9.4 → 11.0 ms；一次把 2000 篇标为已读 22.8 → 36.0 ms。
  - 更早一次运行（未留原始输出）：分别为 11.8 → 12.4 ms 和 30.9 → 44.6 ms。
  - 两次相对增幅：upsert 5–17%，批量已读 44–58%。批量已读要为每篇改一条索引项。
- **升级**：25 万篇建索引约 0.4 秒；库文件从 293,478,400 字节增至 301,854,720 字节（+2.9%）。
- **其他 `entries` 语句**：脚本列出了 20 条（阅读导航、未读选择、标记已读、批量已读 / 归档、刷新、删除、图片本地化），只有两条计划变化，都变快：
  - 单订阅全部标为已读：23.4 → 5.4 ms。
  - 其预览：18.4 → 0.03 ms。
