## 关键变更

### 已确认的决定

- 正式 Web：资料库在服务器上，登录后任何设备获得完整功能；服务器上的 CLI 共用这份资料库。
- 演示站：GitHub Pages，浏览器内存 SQLite + 同一套仓储代码，不保存，刷新即重置，网络禁用。
- 存储：所有平台一个 `library.sqlite3`；逐步从 sqlx 迁到 rusqlite（迁移期 0.39，删除 sqlx 后 0.40）；新基线吸收未发布的 0008 / 0009。
- 兼容性：不兼容旧进程、旧浏览器存储与降级；保留 v0.1.0–v0.1.23 本机资料库的单向导入。
- GUI 与 CLI 仍是两个程序（见 `cli-gui-distribution.md`）。
- 版本：`v0.2.0`。

### 产品边界的表述

“不做文章库同步”保持不变；新增“资料库”定义：每个资料库独立，资料库之间只交换配置。服务器端 Web 是多个入口访问同一资料库，不是同步。

### 阶段 A1：存储基础（未接入）

新增 `rssr-infra::store`（仅原生，rusqlite 0.39），尚无调用者；现有 sqlx 路径不变。

- `store/migrations/0001_baseline.sql`：单库基线。相对 v0.1.x（索引 0001–0009 + 正文 0001）的差异只有：`entries.title_search` 必填；删除标题搜索的触发器与部分索引；`entry_contents` 去掉 `feed_id`、按外键随文章级联删除；删除跨库 GC 队列、未使用的 `sync_sources` 与 `idx_entry_contents_updated_at`；`feeds` 增加刷新序号 `refresh_issued / refresh_published / refresh_diagnosed` 及其顺序约束。v0.2.0 发布前该文件仍可修改。
- `store/migrate.rs`：资料库文件以 `PRAGMA application_id = 0x52535352` 标记，其它非空 SQLite 文件（包括 v0.1.x 库）一律拒绝且不改动；校验和是 CRLF 转 LF 后的 SHA-384；全部待执行迁移与历史记录在一个 `BEGIN IMMEDIATE` 事务内提交；拒绝更新版本建的库、被改动的迁移与不连续的历史。原来的迁移锁文件不再需要。
- `store/connection.rs`：每个连接设置 `busy_timeout` 30 秒与 `foreign_keys`，注册 `fold_for_search`；读连接 `query_only`；文件库切到 WAL 并返回实际生效的日志模式。
- `store/executor.rs`：`LibraryStore` 有 1 个写连接、4 个只读连接（内存库只有 1 个连接，读任务在其上临时设为 `query_only`）；`read` 在一个读事务（同一快照）内执行，`write` 在 `BEGIN IMMEDIATE` 事务内执行，成功才提交；连接与准入许可随任务进入阻塞线程，任务结束才归还（调用方被取消、任务 panic 也一样）；期限由 progress handler 在引擎内执行。连接数从 sqlx 的“两个库 ×（刷新并发 + 4）”降到 5。
- 实测发现：两个连接同时初始化同一个新文件时，切换 WAL 会互相死锁，SQLite 不经 busy handler 直接返回 `SQLITE_BUSY`（15 次中出现 4 次）。打开阶段改为在 30 秒内有界重试（两步都幂等，迁移是单事务）。

### 阶段 A3：持久化刷新序号

`c1864b8` 在应用层加入序号（行为不变），本记录所在提交在资料库存储中实现规则。规则见设计文档“存储”一节。

- 应用层：`RefreshTarget.ticket: RefreshTicket { issued, baseline }`（`UNTRACKED` 为 0）；`RefreshStorePort::begin_refresh(feed_id, expected_generation)` 在刷新开始时领号，默认实现退回 `get_target`、不领号（v0.1.x 存储与浏览器存储保持原行为）；`RefreshCommitOutcome.superseded`；`ActivatedSubscription.ticket`。`RefreshService` 在每个订阅的锁内调用 `begin_refresh`，被取代的 200 报告为“未变化”且不产生图片本地化任务。
- 资料库存储：`begin_refresh` 在一个写事务里领号并读取目标与校验器；激活订阅的事务同时为添加流程的预抓取结果领号；三种提交按设计规则决定写入或报告被取代；没有序号的提交在事务内领号。
- 测试 `test_library_refresh_tickets`（两个 `LibraryStore` 句柄打开同一文件，代表两个进程），11 passed：领号顺序与基线、迟到的 200 被较新的发布取代、过时基线的 304 被丢弃、匹配基线的 304 记录且保留未重发的校验器、过时的失败不覆盖较新的成功、较新失败之后到达的较旧成功发布内容但保留诊断、同一序号提交两次、无序号提交视为最新、激活时领号的预抓取输给之后的刷新、代际不符不给目标、经 `RefreshService` 的真实竞争（抓取期间另一进程发布）报告为“未变化”。每个用例都检查 `0 ≤ P ≤ D ≤ I`。
- 变异：去掉 200、304、失败三条判定之一，发布时总是清除错误，领号或激活不领号，各自被用例捕获。
- 已知重复：`RefreshService` 里的进程内抓取序号（为浏览器存储保留）与持久化序号在原生端重复，阶段 D 删除浏览器存储时一并删除。
- 失败仍写入失败响应的校验器（三端共享的契约，`refresh_contract_records_failure_message_and_fetch_timestamp`）；错误存在期间目标不发送校验器，304 未重发的校验器取自请求本身。

A3 独立评审（`c1864b8` + `8f3fbe0`）：FAIL，2 个阻断项、3 项应修。逐条核对后全部采纳：

- 阻断：304 缺的校验器从库中当前行补齐，而其间一次失败可能已写入失败响应的校验器，结果出现“内容 A + 校验器 E_B”且错误被清除，此后条件请求可以一直得到 304。改为从这次请求发出的校验器补齐（`a_304_after_a_failure_keeps_the_validators_of_the_published_version`）。
- 阻断：无序号的提交在提交时领号，会给旧 304 凭空造出基线、让较早开始的抓取覆盖较新的发布、让旧失败覆盖较新的成功。改为拒绝无序号的提交且不写任何东西；资料库存储的 `get_target` 改为与 `begin_refresh` 一样领号（`a_commit_without_a_ticket_is_refused`）。三端共享的刷新用例原来把同一个目标提交多次，改为每次提交前取新目标（正确语义是每次响应回答各自的请求），在 v0.1 存储、资料库存储与浏览器端都通过。
- 应修：被取代的失败原来仍报告为失败，改为“未变化”（`the_refresh_service_reports_a_superseded_failure_as_not_modified`）。
- 应修：进程内抓取序号会在同一进程的后台刷新写入失败后丢弃添加流程的预抓取结果，而持久化规则本应接受它；进程内序号改为只用于无序号的目标（`a_prepared_fetch_survives_a_failed_refresh_in_the_same_process`）。
- 应修：测试补齐上述组合；领号成本实测见设计文档（约 1.7 毫秒 / 次）。
- 变异：304 从库中行补校验器、接受无序号提交、忽略被取代的失败、预抓取仍走进程内序号，各自被对应用例捕获。`test_library_refresh_tickets` 14 passed。

### A4 导入器的独立评审（Codex gpt-6-astra，max，`d7374f1`）

FAIL，2 个阻断项、4 项应修、2 项待验证。逐条核对：

- 阻断（属实）：所有导入共用固定的临时文件名并无条件删除，没有设计要求的导入锁，一个导入可能发布另一个导入未完成的库。改为“创建锁”：`files::CreationLock` 在 `library.sqlite3.create-lock` 上取咨询锁（`std::fs::File::lock`，即 `flock` / `LockFileEx`，进程退出即释放；锁文件保留），新建与导入都从确认目标不存在到发布全程持锁；暂存文件固定命名、只属于持锁方（`ScratchFile` 借用锁，类型上保证在放锁前清理），开工前先清掉崩溃遗留。
- 阻断（属实）：硬链接失败后的 `exists()` + `rename` 回退不是原子的。发布改为持锁下的同目录 `rename`，不再用硬链接：Android 的 SELinux 策略不允许应用创建硬链接（推断，依据 AOSP `app_neverallows.te`；未在设备上验证），FAT/exFAT 不支持硬链接，原方案在这些地方本来就依赖那条有竞争的回退。
- 应修（属实）：v0.1.2–v0.1.6 的 `last_opened_feed_id` 键被丢弃。源库没有应用状态时，它与 v0.1.6 的列表偏好一起组成应用状态；已有 v0.1.7+ 应用状态时以后者为准。
- 应修（不采纳，记录理由）：v0.1.0–v0.1.6 也给无正文的文章算标题哈希。v0.2 与 v0.1.7+ 的写入者都只在有 HTML 或文本时写正文行，v0.1.7 自己的 0002 迁移也不保留这类哈希；没有正文的哈希在 v0.2 无用途。规则写进模块文档，夹具改成旧版真实写法（无正文也有标题哈希），断言它们不成为正文。
- 应修（属实）：验收快照删掉了 `generation`、没有 `sqlite_sequence`、不比文档时间。新脚本记录并逐项断言（`generation` 保留、高水位不变、文档 `updated_at` 保留——导入器原来写导入时间，现改为保留源时间）。
- 应修（属实）：硬链接已发布后删暂存文件失败会返回错误。随 `rename` 发布消失（发布后没有需要删除的暂存主文件）。
- 待验证 → 属实：缺正文库时对 `SELECT 1 WHERE 0` 调 `execute`，rusqlite 返回上一条语句的 `changes()`，随后无符号相减下溢。改为直接计 0；并定规则：双库布局缺正文库时，只有索引库没有任何 `has_content` 记录才导入，否则拒绝（v0.1.7+ 总是同时建两个库）。
- 待验证 → 属实：rusqlite `run_to_completion` 对 `Busy` / `Locked` 无限重试。改为单步 `step(-1)`，源连接 busy timeout 到期仍忙即失败并提示关闭旧版程序。

### 执行器第 4 轮独立评审（Codex gpt-6-astra，max，`5809b09`）

FAIL（无已确认阻断，但 3 项待验证可能隐藏阻断）。逐条核对：

- F1（属实）：探针与写连接对路径的解释可能不同——Unix 上反斜杠被探针换成 `/`；`file:` 开头的相对路径会被 `Connection::open`（默认带 `SQLITE_OPEN_URI`）当成 URI。改为打开时一次性 `std::path::absolute`，探针、建库、所有连接与重开都用它；连接不带 URI 标志；反斜杠只在 Windows 上转换；非 UTF-8 路径在建库之前就拒绝。
- F2（属实）：同 A4 阻断二，已改。
- F3（属实）：无锁的 `immutable=1` 探针可能撞上其他进程进行到一半的检查点（第 1 页记录的页数大于文件当前页数），SQLite 报 `SQLITE_CORRUPT`，正常资料库被当作外部文件拒绝。`DatabaseCorrupt` 在 2 秒内重试，持续才拒绝；没有 SQLite 文件头（`NotADatabase`）立即拒绝。单元测试用截掉最后一页的库模拟，300 ms 后补回则接受，始终不补回则 2 秒后拒绝。

### A1 / A2 的独立评审（Codex gpt-6-astra，max）

A1（`325365a`）：FAIL，2 个阻断项。逐条核对后全部采纳，修复在 `0a37d1f`：

- F1：先切 WAL 后检查身份，会改动被拒绝的外部库（WAL 切换写文件头）。改为先用只读连接检查身份（只读连接既不能改日志模式也不能回滚热日志），通过后才做任何写操作；新增 DELETE 日志模式外部库逐字节不变的测试。
- F2：期限约束不了短语句循环与锁等待。改为期限从准入时开始计算（排队等阻塞线程也算），等待其他进程写锁的时间受剩余期限约束，打开阶段的 WAL 切换与迁移共用一个 30 秒预算；progress handler 只中断单条长语句，仓储任务必须由输入规模约束。期限到达时刻意不在提交前拒绝：把稍晚完成的刷新判为失败会导致反复重试。
- F3：清理失败的连接被放回池。现在清理后核实状态，失败则丢弃并重新打开替换连接（内存库则连同许可一起退役）；许可在连接归还之后才释放。
- F4：调用方取消不会提前中断。现在每个任务有取消标志：progress handler 据此中断正在执行的语句，任务结束时若调用方已离开则回滚、不提交。
- F5：测试依赖睡眠时序、回归时会挂住。改为任务内握手，加看门狗线程在超时后终止测试进程。
- F6：`Busy` 文案改为不断言超时，`SQLITE_LOCKED` 不再归为 Busy，`QueryReturnedNoRows` 不再全局映射为 `NotFound`。

变异检查：去掉只读身份检查、把清理失败的连接放回池、取消标志不进 progress handler、提交前不检查取消，各自被对应用例捕获；`test_library_store` 连续 15 次 12 passed。

A1 修复复审（`0a37d1f`）：FAIL，2 个阻断项（R1 只读预检仍会为 WAL 外部库创建或改写 `-shm`/`-wal`；R2 已准入的任务在 tokio 阻塞线程池排队时不受期限约束），另有 R3–R7。逐条核对后全部采纳，执行器改为每个连接一个专属工作线程（本记录所在提交）：

- R1、R4：身份预检改为直接读取文件头 100 字节（应用 id、结构 cookie、魔数），不经 SQLite；两个字段来自同一次读取。新增：WAL 模式外部库旁放一个陈旧 `-shm`，拒绝后目录与该文件逐字节不变；非 SQLite 文件被拒绝且不变。残余：外部 WAL 库若全部结构都还在未检查点的 WAL 中（文件头 cookie 仍为 0），会进入迁移再被拒绝，期间 SQLite 会接触其辅助文件。
- R2：不再使用阻塞线程池；任务排队受准入时限约束，超时或调用方离开时仍在排队的任务被取消、永不运行（`a_task_that_times_out_in_the_queue_never_runs`）。
- R3：去掉固定的 `busy_timeout`，改用读取线程上任务上下文的 busy handler，所有锁等待（含 `BEGIN IMMEDIATE`、提交、打开阶段）都止于同一个绝对期限或取消（`waiting_for_another_writer_ends_at_the_deadline`：300 毫秒期限下等待在 3 秒内以 `Busy` 结束）。
- R5：用原子状态机定义提交点（运行 → 提交）；取消只能在它之前生效，之后的结果对离开的调用方未知，契约已改写。
- R6：恢复失败的连接被丢弃，工作线程在下一个任务时重新打开；不再永久减少容量。内存库无法重开时报告失效。
- R7：看门狗在 panic 展开时保持武装；期限测试确认语句确实开始执行。
- 变异：绕过文件头预检、busy handler 忽略任务期限、超时排队的任务照样运行、取消后仍提交、保留恢复失败的连接，各自被对应用例捕获。`test_library_store` 16 passed，连续 20 次稳定。

执行器第三轮复审（`2447241`）：FAIL，2 个阻断项。逐条核对后采纳，修复在 `5809b09`：

- 文件头探针单独打开再关闭了数据库文件：在 POSIX 系统上关闭任意一个指向该文件的描述符，会释放本进程其他 SQLite 连接持有的全部锁（SQLite 为此延迟关闭）。在 WSL 中实测：空闲的 WAL 连接在主文件上持有共享锁，单独打开并关闭该文件后锁消失。身份探测改为经 SQLite 以 `immutable=1` 只读打开读取应用 id；新增仅 Unix 运行的回归测试（子进程用 `F_GETLK` 检查共享锁区间），WSL 中通过，重新引入原始文件读取时失败。
- 文件头“应用 id 与结构 cookie 均为 0”不能证明是空库（`PRAGMA schema_version = 0` 或未检查点的 WAL 都能造成）。新资料库改为在临时文件中建好后以硬链接发布（不覆盖已有文件，文件系统不支持硬链接时退回检查后改名），正式路径上的文件因此总是完整的资料库，身份判定改为严格要求应用 id；空文件与零头外部库都被拒绝且不改动。导入器的发布也改用同一方式（之前的 `rename` 会覆盖已有文件）。
- 其余：工作线程取出任务时核对其可开始的截止时间；取消立即释放任务闭包及其捕获的数据（队列只留小的任务单元）；打开改在独立线程进行，不再使用 tokio 阻塞线程池；提交阶段的表述收窄为“不再接受取消，提交仍可能失败”；`file:` URI 对 `#`、`%`、空格与非 ASCII 字符编码（新增测试，去掉编码时失败）；排队测试加执行标记与同一写队列上的屏障；期限测试的开始信号来自语句内部调用的 SQL 函数。
- `test_library_store`：Windows 19 passed，Linux（WSL）20 passed（多出 POSIX 锁用例）。

## 风险与后续事项

- 未实测：Android 设备上的创建锁、`rename` 发布与首次导入；macOS 上复制旧库到新数据目录后的导入（及 v0.1 数据在应用包内的具体位置）；v0.1.0–v0.1.6 官方程序写出的库（只有用已发布迁移文件构造的夹具）；大资料库导入的耗时、峰值内存与磁盘占用。
- 已知：两个旧库快照不是同一时刻（要求先关闭旧进程）；`library.sqlite3.create-lock` 会一直留在数据目录；等待创建锁最多 120 秒，超大旧库的导入若更久，同时启动的另一个程序会报错（重启即可）；不覆盖目标的保证只在遵守创建锁的程序之间成立。
- 下一步：本轮修复（`8c0e20d` 之后）送独立复审；之后进入阶段 B。
- 基线保留了 v0.1.x 的全部文章索引，其中 `idx_entries_title`、`idx_entries_published` 等是否仍被查询使用未核实；按真实查询的 `EXPLAIN QUERY PLAN` 评估后再删，不在 A1 处理。
- 设计中的已知代价（自写执行器与迁移器、CLI 绕过服务器协调、单文件写锁争用、断代等）列在决策记录“已知代价”一节。
