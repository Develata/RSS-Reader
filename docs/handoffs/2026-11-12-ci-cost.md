## 工作摘要

Develata 要求通过并行、复用和缓存，减少 CI 的算力消耗与运行时长。依据 2026-11-02 两次完整 CI run 的 job / step 用时，做了七项改动：纯文档改动跳过各模块；14 个 wasm 浏览器契约 job 合并为一个；两个 web-ui job 重新分配套件；7 个 native-module job 合并为 3 组；apt 下载按 runner 镜像缓存；Rust cache 只由 main 写入；release-ui-runner 加 Rust cache。经 Codex 独立评审后修正了 4 项问题。

## 关键变更

### 基线（已核实，来自 GitHub API）

- main run 41490548122：33 个 job，合计 2643 job·秒，墙钟约 9 分钟。PR run 41488988497：合计 2715 job·秒。
- 关键路径是 `web-smoke`（约 170 秒）→ `web-ui (default)`（346–366 秒）。后者的单个步骤里，默认主题 regression 197 秒，acceptance 117 秒，theme-matrix 和 feed-smoke 各约 4 秒；`web-ui (amethyst-glass)` 只有 102–174 秒。
- 14 个 `wasm-browser-contract` job 合计 570–650 秒，harness 实际运行只有 159–173 秒（单个最长 18 秒）。其余时间花在 runner 启动、Rust 工具链、产物下载和 Chrome 准备上；构建 job 上传产物另需 22 秒。
- `rssr-app` 的 apt 安装耗时 49 秒，带字体的浏览器准备每个 job 15–23 秒（不带字体时 3–6 秒）。PR #66 的 4 个失败检查都在 apt / 浏览器准备阶段，原因是 `Temporary failure resolving 'security.ubuntu.com'`。
- `release-ui-runner` 没有 Rust cache：Ubuntu 上 cargo 约 12 秒、验收脚本 72 秒；Windows 上 cargo 约 54 秒、验收脚本 105 秒。
- 仓库的 14 个缓存（4.5 GB）全部属于 `refs/pull/66/merge`，main 的缓存已因 7 天无访问被清除。PR 范围的缓存其他 ref 读不到。
- 按创建时间取最近 30 个已合并 PR（`gh pr list --state merged -L 30`），有 7 个只改文档（#64、#62、#45、#44、#37、#36、#35），却都跑了完整 CI；按合并时间取则是 6 个（不含 #35）。

### 改动

- **纯文档跳过**：`workspace` job 用完整 Git diff 判断（PR 比较合并提交与其第一父提交，main push 比较 `before` 与当前提交，`--no-renames` 使改名也算删除旧路径）。只有每个改动文件都是 `docs/`、Markdown 或 `LICENSE`，且不在 `vendor/` 下时，才判定为纯文档；没有可比较的基准或判断出错时一律全跑。其余 job 都 `needs: workspace` 并在纯文档时跳过；`lint-and-test` 只在 `workspace` 成功且判定纯文档时接受 skipped，任何失败仍拒绝。已核对：没有测试或构建读取 docs 或 Markdown，只有注释提到；`build_id` 本来就排除文档。（初版用 workflow 的 `paths` 过滤，Codex 评审指出它最多只看 3000 个文件，已改掉。）
- **wasm 契约合并**：去掉 `wasm-contract-build`。新的 `wasm-browser-contract` 单 job 先 `--prepare`，再对每个 harness 依次 `--prebuilt`，失败不中断其余，最后列出全部失败项。每个 harness 用 `timeout --kill-after=30s 5m`（平时不到 20 秒）；运行步骤内部限 55 分钟，放不下下一个 harness 时，其余记为“未运行”并判失败，保证汇总总会输出。不再上传、下载产物。`lint-and-test` 的 `needs` 已同步。
- **web-ui 重新分配**：matrix 改为 `include`。三个不带 `--preset` 的套件挪到 amethyst-glass job，各为独立步骤（`!cancelled()` 且共享构建就绪即运行），前一个失败不影响后一个；log 目录改为固定名（`target/ci-ui/theme-matrix` 等），artifact 路径改为 `target/ci-ui/*/…`。`theme-matrix` 自行遍历各主题，其余两个用默认主题。
- **apt 缓存**：新增 composite action，按 `ImageOS` / `ImageVersion` / 架构 / 包请求做键，缓存一次联网安装用到的软件包列表与 `.deb`。命中时恢复二者，由 `apt-get install --no-download` 规划并安装，依赖顺序（含 Pre-Depends）交给 APT，文件按列表校验；缺文件或失败则用 `--fix-broken` 回到联网安装。（初版直接 `dpkg -i`，评审指出 Pre-Depends 顺序风险，已改。）两条路径最后都核对每个请求的包处于 `installed` 状态。没有镜像标识时不缓存。
- **Rust cache 只由 main 写**：CI 中所有 `Swatinem/rust-cache` 加 `save-if: github.ref == 'refs/heads/main'`，与 `pages.yml` 一致。
- **release-ui-runner cache**：`workspaces: scripts/release-ui -> ../../target/release-ui-runner`。验收脚本在 fixture 仓库里的真实 cargo 构建不受此影响。
- **native-module 分组**（Develata 2026-11-12 同意）：7 个 job 改为 3 组。`rssr-app`（需 GTK / WebKit）、`rssr-infra`（测试最长）各一组，其余 crate（含今后新增的）一组。每个 crate 仍单独 `-p` 检查，Cargo 只按该 crate 的 feature 解析；同组只是复用已编译的 crate。某 crate 失败不中断其余，最后点名。分组在 `workspace` job 里由 `cargo metadata` 生成，并断言覆盖全部成员。

## 结果

- 以下是按基线推算的预期效果，尚未验证。每次完整 run 约节省 500–550 job·秒（约 20%）：wasm 约 390 秒、apt 约 100 秒、release-ui 约 45 秒。墙钟预计从约 9 分钟降到约 7 分钟，主要来自 web-ui 关键路径缩短约 2 分钟。纯文档 PR 不再消耗 CI。

## Codex 评审（2026-11-12，对 a66e32b1）

- 结论：没有阻断问题，4 项 SHOULD_FIX 全部采纳：`paths` 过滤的 3000 文件上限 → 改为在 workflow 内用完整 diff 判定；wasm 总预算不足以让其余 harness 运行 → 改为单项 5 分钟加步骤预算，并报告“未运行”；`timeout` 不是硬截止 → 加 `--kill-after`；amethyst regression 失败会跳过挪过去的三个套件 → 拆成独立步骤。
- 采纳 NICE_TO_HAVE：“均用默认主题”不准确（theme-matrix 自行遍历主题）；“最近 30 个 PR”写明排序口径。
- 采纳评审的简化建议：apt 命中路径改由 APT 规划事务；native job 分组（经 Develata 同意）。
- 未采纳：每次 `--prebuilt` 重新编译 runner（每次约 1.3 秒，14 次约 18 秒）。省下的时间不值得改动共享脚本。
- 撤回：手册里曾提议 Windows release-ui 只在 `scripts/release-ui/**` 变化时运行。评审指出验收还读取外层 launcher 与 workspace metadata，而且 job 跳过会让汇总检查失败，因此不做。
- 待验证：apt 命中路径与预期节省都要等真实 run（见下）。
