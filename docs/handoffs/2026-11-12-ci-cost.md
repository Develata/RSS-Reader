## 工作摘要

Develata 要求通过并行、复用和缓存，减少 CI 的算力消耗与运行时长。依据 2026-11-02 两次完整 CI run 的 job / step 用时，做了六项改动：纯文档改动不触发 CI；14 个 wasm 浏览器契约 job 合并为一个；两个 web-ui job 重新分配套件；apt 下载按 runner 镜像缓存；Rust cache 只由 main 写入；release-ui-runner 加 Rust cache。

## 影响范围

- 模块：
  - `.github/workflows/ci.yml`
  - `.github/actions/install-apt-packages/action.yml`（新增）
  - `.github/actions/setup-browser-tests/action.yml`（字体改用上面的 action；Pages 工作流同样受益）
- 平台：
  - CI（Ubuntu / Windows runner）
- 额外影响：
  - `docs/testing/mainline-validation-matrix.md`、README 的 CI 说明

## 关键变更

### 基线（已核实，来自 GitHub API）

- main run 41490548122：33 个 job，合计 2643 job·秒，墙钟约 9 分钟。PR run 41488988497：合计 2715 job·秒。
- 关键路径是 `web-smoke`（约 170 秒）→ `web-ui (default)`（346–366 秒）。后者的单个步骤里，默认主题 regression 197 秒，acceptance 117 秒，theme-matrix 和 feed-smoke 各约 4 秒；`web-ui (amethyst-glass)` 只有 102–174 秒。
- 14 个 `wasm-browser-contract` job 合计 570–650 秒，harness 实际运行只有 159–173 秒（单个最长 18 秒）。其余时间花在 runner 启动、Rust 工具链、产物下载和 Chrome 准备上；构建 job 上传产物另需 22 秒。
- `rssr-app` 的 apt 安装耗时 49 秒，带字体的浏览器准备每个 job 15–23 秒（不带字体时 3–6 秒）。PR #66 的 4 个失败检查都在 apt / 浏览器准备阶段，原因是 `Temporary failure resolving 'security.ubuntu.com'`。
- `release-ui-runner` 没有 Rust cache：Ubuntu 上 cargo 约 12 秒、验收脚本 72 秒；Windows 上 cargo 约 54 秒、验收脚本 105 秒。
- 仓库的 14 个缓存（4.5 GB）全部属于 `refs/pull/66/merge`，main 的缓存已因 7 天无访问被清除。PR 范围的缓存其他 ref 读不到。
- 最近 30 个合并的 PR 中有 7 个只改文档（#64、#62、#45、#44、#37、#36、#35），却都跑了完整 CI。

### 改动

- **纯文档跳过**：`push` / `pull_request` 加 `paths` 过滤，排除 `docs/**`、`**/*.md`、`LICENSE`，但 `vendor/**` 仍然触发。必须在 workflow 层跳过，因为 job 层的跳过会让 `lint-and-test` 失败。已核对：没有测试或构建读取 docs 或 Markdown，只有注释提到；`build_id` 本来就排除文档。
- **wasm 契约合并**：去掉 `wasm-contract-build`。新的 `wasm-browser-contract` 单 job 先 `--prepare`，再对每个 harness 依次 `--prebuilt`（每个 harness 限时 15 分钟），失败不中断其余，最后列出全部失败项。不再上传、下载产物。`lint-and-test` 的 `needs` 已同步。
- **web-ui 重新分配**：matrix 改为 `include`。三个与主题无关的套件挪到 amethyst-glass job，log 目录改为固定名（`target/ci-ui/theme-matrix` 等），artifact 路径改为 `target/ci-ui/*/…`。这几个套件原本就以默认主题运行，没有加 `--preset`。
- **apt 缓存**：新增 composite action，按 `ImageOS` / `ImageVersion` / 架构 / 包请求做键，缓存下载的 `.deb`。命中时用 `dpkg -i` 离线安装，失败则用 `--fix-broken` 回到联网安装。两条路径最后都核对每个请求的包处于 `installed` 状态。没有镜像标识时不缓存。
- **Rust cache 只由 main 写**：CI 中所有 `Swatinem/rust-cache` 加 `save-if: github.ref == 'refs/heads/main'`，与 `pages.yml` 一致。
- **release-ui-runner cache**：`workspaces: scripts/release-ui -> ../../target/release-ui-runner`。验收脚本在 fixture 仓库里的真实 cargo 构建不受此影响。

## 结果

- 以下是按基线推算的预期效果，尚未验证。每次完整 run 约节省 500–550 job·秒（约 20%）：wasm 约 390 秒、apt 约 100 秒、release-ui 约 45 秒。墙钟预计从约 9 分钟降到约 7 分钟，主要来自 web-ui 关键路径缩短约 2 分钟。纯文档 PR 不再消耗 CI。
- 首次运行会是冷缓存：wasm 与 release-ui 的 cache 键是新的，main 上的缓存也已过期。合并后的第一次 main push 会写入新缓存，之后的 PR 才能命中。

## 风险与后续事项

- `dpkg -i` 离线安装依赖“同一镜像版本缺的包集合一致”这一前提；ImageVersion 变化时缓存自动失效。真实 runner 上的命中路径需要观察一次。
- `save-if` 的代价：main 缓存过期后，PR 的多次推送都从冷缓存编译。
- 未采纳：把 7 个 `native-module` job 合并。`-p` 逐包构建能发现 feature 统一掩盖的问题，按包拆分看起来是有意设计；合并能省下重复编译和 job 开销，但需要 Develata 决定。
- 可考虑把 `release-ui-runner` 的 Windows job 改为仅在 `scripts/release-ui/**` 变化时运行。
