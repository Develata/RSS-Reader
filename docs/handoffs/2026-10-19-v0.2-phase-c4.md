## 工作摘要

正式 Web 构建不再把资料库放在浏览器里，而是经 `HttpBackend` 调用服务器 `rssr-web` 的 `/api/v1`。设计与决定见 [阶段 C 计划](../design/v0.2-phase-c-plan.md) 的“C4 的实施设计”一节（两轮独立设计评审，第二轮 PASS）。C4 分三步：C4a 协议、传输与服务器；C4b 界面的恢复行为；C4c 真实服务器上的浏览器回归、CI 与文档。

## 关键变更

### C4a 协议、传输与服务器

- 协议（`rssr-api`）：
  - `ErrorCode::OutcomeUnknown`（线上 `outcome_unknown`，HTTP 504）：写操作可能已生效、却无法确认。客户端在写请求发出后没有收到完整、可解析的本协议回答时产生它；服务器在图片本地化超过时限时返回它（最后一次写回可能落在时限上，设计评审 C4D-R1 B1）。准入阶段的“繁忙”仍是 `unavailable`。
  - `BackendError.reason`（线上缺省为空）：只在 `outcome_unknown` 上使用，目前唯一取值 `unauthenticated`——任务被接受之后会话失效时，界面据此要求重新登录（R2-01）。
  - `protocol::Session { csrf_token }`：`/api/v1/session` 的回答，服务器改用它构造。
- feature（`rssr-infra`）：
  - `browser-store` 门控 wasm 上只有浏览器内资料库用到的部分：浏览器适配器、`composition`、feed 解析与读取（`feed_body`、`feed_normalization`、`feed_structure`、`xml_declaration`）、`opml`、`remote_failure`、订阅探测。正式 Web 构建里这些代码不存在；三个 wasm 契约 harness 声明 `required-features = ["browser-store"]`，运行器带上该 feature。
  - `http-backend` 门控 `http_backend` 模块（wasm 上另加 `gloo-timers`）。`rssr-app` 的 wasm 依赖打开它；`pages-demo = ["rssr-infra/browser-store"]`；`rssr-web` 只在测试里打开它。
  - 依赖图门禁新增 `the_formal_web_build_has_no_browser_store`：正式 Web 解析出的 `rssr-infra` feature 只有 `http-backend`，演示站两者都有。
- `HttpBackend`（`rssr-infra/src/http_backend.rs`，原生与 wasm 共用一份）：
  - 每个请求带 `X-RSSR-Build`；写请求带 CSRF 令牌，第一次写之前从 `/api/v1/session` 取得并缓存；回答 `csrf_mismatch` 时重取一次、重发一次（服务器在应用处理之前拒绝）。取令牌得到的协议错误原样返回，只有传输或解码失败才是 `network`。
  - 结果未知：写请求发出后断线、超时、回答截断或停滞、HTML 错误页、回答过长或成功回答的内容不对，都是 `outcome_unknown`，从不自动重发。原生客户端能分辨“连接没建立”（`network`）；浏览器的 fetch 失败一律当作已发出。读请求的同样情况是 `network`。原生客户端关闭自动重试与重定向（`HttpBackend::native_client`）。
  - 回答的上限是协议的一部分（`rssr-api::protocol`，第一、二轮评审 C4A-02、C4A-R2-02）：普通回答 `MAX_ANSWER_BYTES`（64 MiB，阅读条目可能内嵌图片，导出含全部订阅），轮询 `MAX_JOB_STATUS_BYTES`，取令牌、任务创建与错误回答 `MAX_SMALL_ANSWER_BYTES`（64 KiB）。服务器不发超过上限的回答（见下），客户端边收边数解码后的字节，超过即不再读：读请求 `network`，写请求结果未知，过长的错误回答当作不是本协议的回答。原生上声明的长度就是回答体自己的（压缩的回答解码时去掉了它），超过即不读；浏览器里声明的是压缩后的长度、交来的却是解码后的内容，不看它（C4A-R2-03）。限定的是已收下的解码后字节的长度，不是内存：浏览器里 reqwest 先把浏览器交来的一块（大小由浏览器决定）整个复制再计数，这些块、浏览器自己的缓冲与已收字节多分配的容量都不在上限之内（C4A-R2-04、C4A-R3-02）。
  - 后台任务：创建得到任务 id（拿不到，或不是协议的形式——32 位小写十六进制——即结果未知、不轮询，C4A-03），以 10 秒长轮询直到终态；轮询失败在第一次之后最多重试 5 次（间隔 1、2、4、8、16 秒），连续第 6 次失败即结果未知，成功的轮询把计数清零；任务自己的失败照原样返回、不重试；`status_unavailable` 即结果未知；轮询得到 `unauthenticated` 即结果未知并带原因；终态结果的种类不对即结果未知。
  - 时限：普通 30 秒、轮询 20 秒、图片本地化 70 秒（`Timeouts`，测试用短的）。`ensure_auto_refresh_started` 是空操作。
- 服务器（`rssr-web`）：回答不超过协议的上限（C4A-R2-02）：结果超过 `MAX_ANSWER_BYTES` 不发送，读请求回答 `too_large`，写请求（已执行）回答 `outcome_unknown`；错误消息发送前截短到 1 KiB（`MAX_MESSAGE_BYTES`，后台任务的失败原本就截短），错误码保留。删除 `/feed-proxy`（路由与 `proxy` 模块及其隔离测试夹具）、`rssr_web_gate` cookie、`GET /session-probe`；`reqwest` 只剩测试使用，移到 dev-dependencies。登录后 `/feed-proxy` 与其他未知路径一样得到 404，未登录时重定向到登录页。
- 网页端（`rssr-app`）：非演示站构建 `HttpBackend`（地址取页面 origin，构建标识来自 `build.rs`，只在 wasm 目标上计算）；演示站构建原来的浏览器内 `LocalBackend`。删除本地浏览器门禁（`web_auth.rs`、`web_auth_browser.rs`、门禁界面与状态），以及只有它用到的 `sha2`、`urlencoding` 依赖；外壳启动时直接读设置。界面对 `outcome_unknown`、`unauthenticated`、`build_mismatch` 的专门处理属于 C4b，这一步里它们照旧显示为错误消息。
- 脚本与 CI：
  - `scripts/wasm_contract_runner.rs` 拼 cargo 参数时带 `--features browser-store`（及其测试）。
  - `scripts/run_rssr_web_auth_assertions.sh` 不再断言门禁 cookie 与 `/session-probe`，改用 `/feeds` 检查会话；release UI runner 的假服务器与请求序列随之更新。
  - release UI runner 去掉 `proxy-feed` 阶段与只为它存在的 `--skip-external-feed` 选项。
  - CI 删除 `feed-proxy-isolation` 任务及汇总任务里对它的引用。
  - 留给 C4c：CI 的 `web-ui` 任务、release UI runner 的静态阅读主题矩阵与小视口任务、`run_static_web_*`、`run_web_spa_regression_server.sh`、`scripts/browser/*_acceptance.cjs` 与 `rssr_small_viewport_assertions.mjs`（都靠 Python 静态服务器加 `localStorage` 夹具与本地门禁），以及 `run_rssr_web_browser_feed_smoke.sh`（需要独立的 feed 夹具服务与出站例外）。它们在 C4a 之后不适用于正式 Web，C4c 改写；文档中指向已删脚本的链接也在 C4c 修正。

### C4a 第二轮代码评审（Codex gpt-6-astra，max，`b89a7d4..5810fb8`）与修复

结论 FAIL：1 个阻断（C4A-R2-01）、2 个应修、1 个待核实。第一轮的 C4A-03、C4A-04 判为已解决，C4A-01、C4A-02 部分解决。评审确认：真实中间件的拒绝发生在执行之前，计数是后端的执行次数；所有回答（含错误、取令牌、任务创建与轮询）都经限长读取；时限覆盖回答体的接收；`Call` 的重构、`Observed` 的委托、新的 dev 依赖与锁文件改动没有引入问题；`with_csrf_token` 可以保持公开。意见逐条核实属实：

- C4A-R2-01（阻断）几个测试分不清它声称的性质：停滞的回答在 5 秒后由假服务器自己断开，去掉客户端的时限，两个停滞测试照样通过；放弃等待的测试收到一次轮询后等 50 毫秒就放弃，不能说明那时已在退避等待里。修复：
  - 假服务器不再自己结束停滞的回答，一直等到客户端关闭连接，并记下被放弃的次数；调用都套上 5 秒的外限（`ended`），只有客户端自己的时限能让它们按时结束。变异检验：去掉请求时限，两个停滞测试失败。
  - 放弃等待分两种状态各测一次：轮询进行中（服务器扣住轮询、客户端的时限是 30 秒）放弃，服务器看到这次轮询的连接被关闭，之后没有别的请求；退避等待中（第一次轮询立即失败、下一次在 1 秒后）放弃，300 毫秒时确认还没有第二次轮询，放弃后 2 秒内没有轮询；对照组不放弃，第二次轮询照常到来。
  - 补上“成功的回答是不完整的 JSON”（`{"broken`）：写请求结果未知、只发一次，读请求 `network`。
- C4A-R2-02（应修）客户端的上限与服务器能产出的回答不相容。评审的例子：阅读本地化把同一张图片的 data URL 写进 `<picture>` 的每个 `<source>`（各两次）与 `<img>`，一张 6 MiB 的图片在四个 `<source>` 下就是 72 MiB；导出随订阅累积没有上限；错误消息可以引用 70 KiB 的未知字段名，超过 64 KiB 的错误回答被当成结果未知。修复：上限写进协议，服务器遵守它（见上），客户端用同一组常量；轮询的上限去掉了随意加的 4 KiB。超过 64 MiB 的阅读条目与导出在网页端得到明确的 `too_large`（桌面端不受影响），见风险。测试 `the_server_keeps_its_answers_within_the_bound`（真实路由，上限设为 16 字节：读 `too_large`；写 `outcome_unknown` 而写入已执行；70 KiB 未知字段的导入错误保留 `invalid_input`，消息截短）。变异检验：去掉服务器的上限或截短，该测试失败。
- C4A-R2-03（应修）声明长度的预检在原生与浏览器上比较的不是同一种长度（见上）。改为只在原生上预检。测试：解码后正好 64 KiB、压缩后（stored 块的 gzip）超过 64 KiB 的回答在原生上照常读取，多 1 字节即拒绝。浏览器上的行为没有测试（C4c）。
- C4A-R2-04（待核实）浏览器里 reqwest 先复制整块再交给计数，计数只限定累计长度，不限定峰值内存。按评审建议如实收窄说明（模块注释与上文）；测试改为“回答没收完就已放弃”：不声明长度的过长回答发完后连接一直不关，客户端的时限是 30 秒，调用在 5 秒内结束才算通过。变异检验：去掉限长，该测试失败。同时补了正好等于上限（声明、不声明长度、压缩）的成功与过长的写请求错误回答（结果未知、只发一次）。

### C4a 第三轮代码评审（Codex gpt-6-astra，max，`5810fb8..bc7628c`）与修复

第一次运行在约 9 分钟时因 OpenAI 的模型容量不足退出（退出码 1，没有结论），换一个评审包重跑后完成。结论 FAIL：1 个阻断（C4A-R3-01）、1 个应修、1 个可选。第二轮的 C4A-R2-02、C4A-R2-03 判为已解决，C4A-R2-01、C4A-R2-04、C4A-01、C4A-02 部分解决（剩下的就是下面三条）。评审确认：服务器经 `/api/v1` 发出的回答（`run` 的结果、经 `failure` 的所有错误含中间件与协议自己的、任务状态、会话、任务创建）都在上限之内，分类正确；客户端对同一种回答用同一个常量；原生专用的预检两端都正确；停滞的回答只由客户端放弃，`ended` 限定了每次调用；不声明长度的过长回答确实在收完之前放弃。意见逐条核实属实：

- C4A-R3-01（阻断）退避等待中放弃的测试仍不能说明被放弃的那次调用已进入退避：收到一次轮询、等 300 毫秒，与“还在处理第一次失败”同样相容。修复：`rssr-infra` 的 `http_backend` 加只在其单元测试里编译的退避闸门（线程局部，`backoff_gate`）：退避不再看时钟，而是记下开始并等测试放行。新单元测试 `a_wait_given_up_between_polls_polls_no_more`：看到退避开始后放弃，再放行，300 毫秒内没有第二次轮询，也没有第二次退避；对照组放行后第二次轮询与第二次退避照常到来。变异检验：失败的轮询之后另起一个分离的任务等退避再轮询（模拟放弃后仍会轮询的回归），测试在“放弃之后什么都没有”的断言处失败（轮询 2 次）。`rssr-web` 的取消测试只保留“轮询进行中”那一种（改名 `a_wait_given_up_during_a_poll_sends_nothing_more`）。`rssr-infra` 的原生 dev 依赖 tokio 加 `io-util`（测试里的假服务器）。
- C4A-R3-02（应修）浏览器上“上限加一块”的内存说法仍然过头：reqwest 持有 JavaScript 的块时又分配同样大的 Rust 缓冲，且累计的只是长度不是容量。改为只说限定的是已收字节的长度，并写明不在上限之内的部分（模块注释与上文）。
- C4A-R3-03（可选）记录的两处细节不符：测试组数（此前的统计把名字里含 “test result” 的测试也算作一组，实为 56 组；通过与忽略的数目没有受影响，已逐组复核）与上一节一处变异的失败位置。都已更正。复跑该变异并保存输出（`evidence-c4a-r3/mutation-no-shortening.log`）；同时在服务器上限测试里补了 2 KiB 字段名的用例，单独检验截短：现在去掉截短，失败在截短的断言（消息 2181 字节）。

## 风险与后续事项

- C4a 之后到 C4c 之前，CI 的 `web-ui` 任务与依赖 Python 静态服务器的浏览器脚本不适用于正式 Web（设计中已说明，三步一起合并）。
- 演示站的浏览器适配器里仍有“先试 `/feed-proxy` 再直连”的抓取代码；演示站禁用网络，这段代码不会运行，阶段 D 随浏览器存储一起删除。
- “时限落在写回上”用模拟的写回测试（第一轮评审 C4A-01），没有让真实存储的写入正好落在时限上。
- 超过 64 MiB 的回答在网页端打不开（`too_large`，C4A-R2-02）：阅读本地化把同一张图片写进 `<picture>` 的每个 `<source>`（各两次）与 `<img>`，正文可以远大于图片本身；导出随订阅累积。桌面端照常。去掉本地化里的重复写入（只写实际选中的来源，或限制改写后的大小）是后续的设计项，同时减小桌面端资料库的体积。
