# Headless Active Interface 设计目标

## 目的

这份文档定义 RSS-Reader 的 headless active interface 边界及演进约束，当前实现核对于 2026-09-30。

它回答的是：

- 什么叫 `headless active interface`
- 当前前端与 CLI 如何共享业务语义
- 重构后哪些东西必须稳定，哪些东西可以自由重排
- 为什么这会支持极端 CSS 视觉重构
- 每完成一个模块后，怎样证明视觉和体验没有漂移

如果要看当前 repo 里已经落地的实现版边界，而不是目标本身，见：

- [UI Shell / Bus / Page Facade 边界](./ui-shell-bus-page-facade.md)

## 核心定义

### active interface

active interface 指一组稳定、可调用、可组合的前端活动接口。它们表达的是用户可触发的
业务动作，而不是某个具体按钮、卡片或 DOM 结构。

例如：

- 添加订阅
- 删除订阅
- 刷新单个订阅 / 刷新全部订阅
- 标记已读 / 切换收藏
- 导入配置 / 导入 OPML / 下载 WebDAV 配置
- 打开阅读页 / 返回上一页 / 跳到上一篇

### headless

headless 指这些活动接口不依附于某一种具体视图结构。

它们可以被以下任意载体触发：

- 页面按钮
- 表格单元格
- 工具栏
- 右键菜单
- 快捷键
- 命令面板
- CLI

因此，UI 只是动作的渲染层，而不是动作的定义层。

### view shell

view shell 指负责路由、布局、主题、动画、焦点管理和信息呈现的界面外壳。

它负责：

- 页面切换
- 组件布局
- CSS class / `data-*` 暴露
- 视觉状态展示

它不负责：

- 直接实现业务动作
- 在点击闭包里临时拼接业务规则
- 把命令语义藏在 DOM 结构里

## 当前状态与目标状态

### 当前状态

当前页面已经使用 facade/session、`UiCommand`、`execute_ui_command` 和 `UiIntent`；
`ui/shell` 管理导航、全局搜索和手动刷新生命周期。页面输出稳定的语义 DOM，CSS 负责呈现。

GUI 与 CLI 通过 `AppUseCases` 共享 application 用例。`UiCommand` 是 GUI 内部命令，
CLI 不依赖 Dioxus，也不需要通过 UI bus；可复用的是业务语义，而不是路由或焦点状态。
命令面板等载体只是可扩展方向，当前未实现。

实现细节见 [UI Shell / Bus / Page Facade 边界](./ui-shell-bus-page-facade.md)。

### 目标状态

重构完成后，前端应满足：

1. 所有非显示性动作都先定义为统一的 Rust 命令接口。
2. 页面组件只负责：
   - 收集输入
   - 分发命令
   - 订阅结果状态
3. 同一动作可被 GUI、CLI、快捷键和未来命令面板复用。
4. CSS 可以自由把动作入口重排为：
   - 表格
   - 单框控制台
   - 仪表盘
   - 极简工作台
5. 任何模块级重构都不得改变现有用户可见视觉与体验，除非规格明确批准。

## 目标架构

## 命令层

所有非显示性行为都应首先建模为稳定命令。

最低要求：

- 每个命令只表达一个清晰语义
- 命令名称与 UI 无关
- 命令不以按钮文本、DOM 结构或页面位置命名

当前 `UiCommand` 命令族为 `Shell`、`Entries`、`Reader`、`Feeds`、`Settings`。
配置交换归入设置命令，导航由 shell / 页面会话承接。不要为符合抽象示例重新拆分现有命令。

## 查询层

除动作外，稳定查询接口也应与视图解耦。

例如：

- 订阅列表查询
- 阅读页导航查询
- 当前筛选结果查询
- 设置快照查询

查询接口应保证：

- 返回稳定视图模型
- 不把数据库结构直接暴露给视图壳

## 视图壳

视图壳应只负责：

- 路由
- 布局
- 可访问性
- 焦点与快捷键
- 视觉状态

视图壳可以非常自由地重排：

- 按钮可以排成表格
- 订阅信息可以变成单行
- 多页内容可以在视觉上合并成统一工作台

但不得：

- 绕过命令层直接实现业务
- 用 CSS 推断业务状态

## 为什么这会支持极端 CSS

一旦动作先于 UI 被建模，CSS 的自由度会显著提高。

届时可以安全支持：

- 把“文章 / 订阅 / 设置”做成极窄页签
- 把文章列表、订阅状态、设置入口压缩成单框工作台
- 用表格、终端风或密集 dashboard 重排同一套功能
- 让单个动作在不同布局中复用，而不需要重新发明行为

也就是说：

- CSS 决定“看起来像什么”
- Rust 命令层决定“动作是什么”

## 迁移非目标

本次重构明确不做：

- 改变产品边界
- 改变路由语义
- 改变业务结果
- 顺便新增 AI / 社交 / 推荐 / 规则引擎
- 以重构名义重做视觉风格

如果某次模块重构顺便改变了视觉、交互节奏或信息层级，它必须先进入规格，而不是作为默
认副作用混入实现。

## 模块级验收门禁

每完成一个模块，必须按以下门禁通过后才可继续：

1. 命令层和视图壳边界已经清楚。
2. 自动化检查通过。
3. 使用项目已有 Playwright / CDP 脚本或 Chrome MCP，对重构前后的真实页面执行同路径验证。
4. 视觉与体验无偏离。

“视觉与体验无偏离”至少包括：

- 页面层级不漂移
- 主要信息顺序不漂移
- 操作触达成本不升高
- 路由切换、按钮反馈、错误提示、筛选与导航行为不回退
- 桌面与小视口下都不出现新增破坏

## 真实浏览器基线要求

真实浏览器验收是涉及界面重构的收口条件；工具选择随当前环境，编译和静态检查不能替代交互与截图验收。

每个模块至少需要：

- 记录重构前基线
- 运行重构后同路径验证
- 检查 Console
- 检查关键按钮、路由与状态提示
- 检查桌面和一个小视口

统一流程见：

- [Headless 重构视觉等价验收](../testing/headless-refactor-equivalence.md)

## 后续演进

订阅、阅读、设置和导航壳的命令迁移已经落地，后续按实际问题调整边界。
保持页面异步结果的身份与代际检查、应用级刷新去重，以及稳定选择器；不为追求统一形状新增全局 store 或要求 CLI 经过 UI。
用户明确批准的视觉优化按约定的新效果验收；纯边界重构仍要求前后视觉等价。
