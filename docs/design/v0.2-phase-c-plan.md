## 现状（2026-10-15 调查）

- `rssr-web` 目前只是静态包托管加登录：
  - 认证：用户名来自环境变量。Argon2 哈希来自环境变量，或来自首次启动时写入认证状态文件（默认 `$HOME/.rssr-web-auth.json`，容器内 `/app/auth/auth.json`）的哈希；部署文档允许初始化后删除密码环境变量。
  - 会话：cookie 是 HMAC 签名的“用户名:到期时间”，服务器不保存会话，退出登录无法吊销已复制的令牌，默认 12 小时。
  - 退出登录是 `GET /logout`；没有 CSRF 与 Origin 校验。登录有失败限速。
  - `/__codex/*` 冒烟辅助路由在开启时会给任何人发会话 cookie（默认关闭）。
- 资料库在每个访客浏览器的 `localStorage` 里；`/feed-proxy` 代抓 feed 以绕过 CORS。
- 出站访问：只有 `/feed-proxy` 检查目标地址，并固定 DNS 结果、逐跳复核重定向、禁用环境代理。
  - 它的判定漏掉了 `192.0.0.0/24`、NAT64 前缀、6to4、Teredo 等形式：实测接受 `192.0.0.1`、`::ffff:192.0.0.1`、`64:ff9b::a00:1`、`64:ff9b:1::a00:1`、`2002:a00:1::1`、`2001::1`。
  - infra 里的 feed 抓取、订阅发现、图片本地化、WebDAV 没有地址检查（适合桌面），但各有自己的重定向、认证、降级与 Referer 规则。
- `Backend` 有 24 个异步操作，外加一个同步的生命周期钩子 `ensure_auto_refresh_started`。只有 `LocalBackend` 一个实现；公开类型已可序列化（B2-D7）。
- 本地化的图片以 `data:` URI 写进正文 HTML、存在库里。
- 自动刷新读一次设置后睡满剩余间隔（最长一年），并在调度循环里直接等待整次刷新结束。
- 存储执行器把每个任务包在事务里，`VACUUM INTO` 不能在其中运行。
- 批量已读的确认在内存里取出整个新选择集，变化时整份放进 `SelectionChanged` 返回，不受预览上限约束。
- 依赖现有接口的脚本与 CI：
  - `run_rssr_web_browser_feed_smoke.sh` 用冒烟辅助路由；
  - `run_rssr_web_auth_assertions.sh` 不带 Origin 登录，并用 `GET` 退出；
  - CI 的 `feed-proxy-isolation` 测试代抓接口；
  - CI 的正式 Web 回归用 Python 静态服务器加 `localStorage` 夹具。
- 镜像只装 `rssr-web`，只准备 `/app/auth`；没有 `/data`、没有 CLI，也不注入构建标识。

## 工作项

### C1 出站访问策略（infra）

所有出站请求（feed 抓取、订阅发现、图片本地化、WebDAV）共用一层地址策略：
- `Unrestricted`：桌面、Android 与普通 CLI 用，保持现状。
- `PublicOnly { allow, deny }`：服务器用，只允许公网地址。

**地址判定**（`rssr_infra::outbound::is_public_address`，已实现）是全局可路由单播地址的允许清单，依据 IANA 特殊用途地址登记，另有几处有意更严：
- IPv4 拒绝：
  - `0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`、`172.16/12`、`192.0.0/24`、`192.0.2/24`；
  - `192.88.99/24`、`192.168/16`、`198.18/15`、`198.51.100/24`、`203.0.113/24`；
  - `224/4`、`240/4`。
- IPv6：
  - 众所周知的 NAT64 前缀 `64:ff9b::/96` 按内嵌的 IPv4 判定。IPv6-only 服务器借 DNS64 访问 IPv4-only 站点时就是这种地址；RFC 6052 禁止它表示非全局 IPv4。
  - 其余只接受 `2000::/3`，并排除文档 `2001:db8::/32` 与 `3fff::/20`、IETF 协议分配 `2001::/23`、6to4 `2002::/16`。
  - IPv4 映射、已废弃的 IPv4 兼容、本地 NAT64 `64:ff9b:1::/48`、唯一本地、链路本地、站点本地、组播、回环与未指定地址都在 `2000::/3` 之外，一律拒绝；IPv4 映射即使内嵌公网地址也拒绝。
- 有意比登记更严：整个 `192.0.0/24` 与 `2001::/23`（其中少数任播服务全局可达，阅读器用不到）、6to4 与 Teredo（登记标为不适用，二者可隧道到任意 IPv4）。用例冻结这些正反例。
- 网络专用的 NAT64 前缀（RFC 6052 §3.4）位于普通全局地址里，无法从地址识别。部署若把这样的前缀翻译到内网 IPv4，必须在出口防火墙拦截，或在策略文件的 `deny` 里列出。部署文档写明这一前提。

**放行与拒绝清单**（策略文件里）：
- `allow` 的条目是地址段或主机名：
  - 主机名条目：对这个主机名（规范化后完全相同）的请求，其解析结果不做公网检查，用于放行内网的 WebDAV；
  - 地址段条目：放行落在其中的地址。
- `deny` 的地址段优先于一切。

**执行点**：每个请求的每一跳都检查，三处缺一不可：
1. 发出前：检查初始 URL 的协议（只允许 http/https）与字面地址。字面 IP 不经过解析器，所以必须单独检查。
2. 解析：自定义 DNS 解析器只返回通过检查的地址；任一应答被拒绝，整个请求就失败，防止混合应答与 DNS 重绑定。
3. 重定向：每一跳的目标 URL 再检查协议与字面地址；主机名照样走解析器。

传输层：
- `PublicOnly` 的客户端禁用环境代理（否则由代理替我们解析并连接，地址检查失效）。客户端构建失败就失败，不回退到默认客户端。
- 地址策略与各操作自己的规则分开，后者保持不变：
  - WebDAV：同源重定向、拒绝 303、认证头；
  - 图片：禁止降级、Referer 只留源；
  - feed：重定向次数上限。
- 体积上限不变。每个请求一个总时限，涵盖解析、全部重定向与读正文。

检查一律针对解析后的 URL（`url::Host`），不另行解析主机文本：十进制、十六进制、八进制、缩写、百分号编码的 IPv4，带 IPv4 的 IPv6，以及用户信息里像主机名的部分，都按解析器的结果判断。

验收：四条请求路径各自测试三种情形——无重定向的私有字面地址、混合 DNS 应答（任一应答被拒绝即整体失败，与应答顺序无关）、重定向到私有地址；另测上述各种字面地址写法与末尾带点的主机名。断言被禁止的本地监听方收到 **零** 个连接。环境代理变量的忽略由构建方式保证（`no_proxy`），不在测试里改动进程环境。

**策略文件 `outbound.json`**（决定 Q3）：
- 数据目录不存在，或其中确实没有这个目录项时，才是 `Unrestricted`。
- 读取方式：以不跟随符号链接、不在 FIFO 上阻塞的方式打开，类型、属主与权限都在这个打开的描述符上检查，并经同一描述符读取，检查与读取之间不能被替换。悬空的符号链接、其他符号链接、FIFO 等非普通文件、无权读取、格式错误一律在发出任何网络请求之前报错退出，不放宽。
- 数据目录路径中间的各级目录不逐级防替换：数据目录属于服务器的运行用户，这是信任模型的前提。
- 信任模型（Unix）：
  - 数据目录与策略文件属于服务器的运行用户，策略文件不允许组或其他用户写；
  - 有策略文件时，服务器与 CLI 在打开 SQLite 之前核对有效用户与数据目录及策略文件的所有者一致，不一致就拒绝运行，避免以其他用户（例如 `sudo`）留下属主不对的 SQLite 附属文件。没有策略文件的数据目录（桌面与普通 CLI）不做这项检查。
- 服务器启动时，在任何出站工作之前，若文件不存在就发布默认策略（只允许公网、无放行）：
  - 完整内容先写入临时文件并同步到磁盘，再以硬链接发布到策略文件名；目标已存在时这一步原子失败，改为读取已有的那份，不覆盖管理员同时放置的文件；
  - 崩溃最多留下从不读取的临时文件 `outbound.json.new-*`，不会留下空的或截断的策略文件。
- 策略文件不属于配置导入导出的内容；资料库备份不含它，恢复后需先重新放置，再运行 CLI。

`/feed-proxy` 随 C4 删除。C1 改动共享的 infra，提交前同时跑 wasm 检查。

C1 的服务器一侧随 C3 接入：服务器在 C3 才打开资料库，届时启动流程先调用 `outbound::ensure_server_policy(data_dir)`，再用 `native_local_backend_with(store, policy)` 建立后端。C1 本身只接入 CLI；桌面与 Android 有意保持 `Unrestricted`。

### C2 认证（`auth.sqlite3`）

认证数据单独存放在数据目录的 `auth.sqlite3`，不在资料库里，资料库备份不包含它：
- 所有者凭据：Argon2 哈希，以及“凭据代数”（每次改密码加一）；
- 会话：不透明令牌，库里只存摘要，带创建时间、最后记录的使用时间与创建时的凭据代数；
- CSRF 令牌：每个会话一个，固定不变。

**实现位置**：认证存储在 `rssr-web` 内（`auth/store.rs`），直接使用 `rusqlite`（与 infra 相同的捆绑 SQLite）。认证是 Web 部署的事，`rssr-web passwd` 与 `rssr-web sessions revoke-all` 也是它的子命令；`auth.sqlite3` 不经过资料库的执行器，认证操作很少，每次在阻塞线程上开一个短连接（WAL，带 busy timeout）。

**凭据初始化与旧部署迁移**（决定 Q1）：
- `auth.sqlite3` 不存在时，按顺序取第一个可用的凭据建立它：
  1. `RSS_READER_WEB_PASSWORD_HASH`；
  2. `RSS_READER_WEB_PASSWORD`；
  3. 旧认证状态文件（`RSS_READER_WEB_AUTH_STATE_FILE`，或其默认路径）里的哈希。
- 建立成功后以库为准，环境变量与旧文件不再读取。旧的 HMAC 会话 cookie 一律拒绝（旧认证卷仍挂载时也一样），升级后需重新登录一次。
- 旧部署升级时，凭据相关的环境变量不用改。但新增必填的 `RSS_READER_WEB_PUBLIC_ORIGIN`（见下），部署文档与 Compose 写明；新数据卷建立成功之前，旧认证卷保持挂载。
- 改密码用 `rssr-web passwd`，从标准输入读入。

**会话**（决定 Q4）：
- 对用户不可见：登录后浏览器自动记住，使用时自动续期，不提供设备或会话列表。
- Cookie 带 `Secure`、`HttpOnly`、`SameSite=Lax`，`Max-Age` 为 180 天，浏览器因此一直保留它（浏览器也可能提前清除）。服务器同样按创建时间执行 180 天的绝对上限，不依赖浏览器。
- 空闲期限：最后使用时间最多每小时写一次库。判断空闲时，在 30 天上加上这 1 小时的记录粒度：会话不会提前过期，最多晚 1 小时过期。
- 时钟：服务器时钟可信（NTP 同步）是前提。
  - 发现时钟回拨（当前时间早于会话记录的最后使用时间 5 分钟以上）时，拒绝并删除该会话，失败时偏于关闭。
  - 会话一旦被判过期（空闲或绝对上限），立即删除，之后的时钟变化不能让它复活。
  - 续期从不把最后使用时间往回改。
  - 写入失败时（C2 第一轮代码评审后补充）：
    - 删除失败的会话，本进程记为待吊销，一直拒绝，再次出示时重试删除；
    - 需要续期却写不进使用时间时，拒绝这次请求：没有记录的使用不放行，空闲期限因此不会提前到来；
    - 服务器启动时清理已经失效的会话，认证库不可写时启动失败；
    - 待吊销记录不跨重启，所以服务器启动时就在数据目录放下运行标记（不依赖出错时还能写入），正常停止（SIGTERM / Ctrl-C）且待吊销全部删掉之后才移除。启动时发现标记（上次异常退出，或停止时仍有删不掉的失效会话），先吊销全部会话：异常退出之后，所有浏览器都要重新登录（C2 第二轮代码评审后补充）。
    - 结束运行时先在锁内关闭认证库，之后的会话操作一律拒绝，标记是否移除只看关闭那一刻；停止的各段有总时限（等待请求 4 秒、收尾 3 秒、关闭运行时 1 秒），收尾超时就保留标记。同一数据目录只能运行一个服务器（排他锁）；命令行子命令照常并发（C2 第三轮代码评审后补充）。
- 原子性：
  - 登录：在一个认证库读事务里，同时读出哈希与凭据代数，用这个哈希核对密码；写入新会话的事务再次核对凭据代数未变。服务器不缓存哈希。
  - 改密码：在一个事务里更新哈希、递增凭据代数、删除全部会话。
  - 续期：只更新仍然有效的会话行，绝不重建已删除的会话。
- 退出登录吊销本会话；改密码吊销全部会话；`rssr-web sessions revoke-all` 只吊销会话、保留凭据，供恢复备份时使用。
- 验收：
  - 用受控时钟测试第 29 天、30 天、30 天 1 小时附近（含整点前后），以及 180 天；
  - 重启后会话仍有效；
  - 时钟回拨 5 分钟以上：会话被拒绝并删除；已过期的会话在时钟回拨后仍无效；
  - 超过 180 天的原始 cookie 重放被拒绝；
  - 退出与续期的两种先后顺序，登录与改密码的两种先后顺序；
  - 旧 HMAC cookie 被拒绝。

**请求校验**：
- 信任的公开来源（scheme、主机、端口）由 `RSS_READER_WEB_PUBLIC_ORIGIN` 给出，生产环境必填。
- 开发环境可以不填，此时服务器只允许监听回环地址，并只信任与监听地址完全一致的来源（`http://127.0.0.1:<端口>`、`http://localhost:<端口>`）；回环主机名上的其他端口或页面不因“是本机”而被信任。
- 写请求的 `Origin` 必须与信任来源完全一致；缺少 `Origin` 或为 `null` 时拒绝。
- 登录前：登录表单是普通的 HTML 表单，同样要求 `Origin` 一致，并保留失败限速；不要求构建标识与 CSRF 令牌。
- 登录后：
  - 页面经 `GET /api/v1/session` 取得 CSRF 令牌。响应带 `Cache-Control: no-store`，不带任何跨源（CORS）头。
  - 每个写请求在 `X-RSSR-CSRF` 请求头里带上令牌。
  - 退出登录是带同样校验的 `POST`。网页端目前没有退出按钮，靠手动访问 `/logout`：`GET /logout` 改为显示一个确认页，页面的表单带上本会话的 CSRF 令牌，提交即 `POST /logout`。
- 保留到 C4：非 `HttpOnly` 的 `rssr_web_gate` cookie 与 `GET /session-probe`。网页端目前靠它们判断有服务器门禁，C4 换成 `HttpBackend` 后一并删除。
- 未登录访问 `/api` 返回 JSON 401；`/api` 不落入 SPA 回退。
- 验收：经由真实的反向代理配置覆盖登录、退出与每个写路由；跨源的导航与 fetch、`null` Origin、同主机的其他来源都被拒绝。

**冒烟与脚本**：

### C3 API（`/api/v1`）与后台任务

**路由**：
- 24 个操作各对应一个路由。请求与结果直接用 application 的公开类型（JSON）；错误体为 `{ code, message, request_id }`。路由、协议版本与错误体定义在 `rssr-api`，服务器与客户端共用。
- 按实际副作用区分读写：读用 `GET`；有副作用的用 `POST` / `PUT` / `DELETE`，包括 WebDAV 拉取与阅读页图片本地化。
- `ensure_auto_refresh_started` 不是路由：`HttpBackend` 里是空操作，服务器启动时开始唯一的定时刷新（C5）。

**后台任务**（决定 Q2）：
- 五个操作走后台任务：刷新全部、刷新单个订阅、添加订阅（含首次刷新）、WebDAV 上传、WebDAV 下载。其余 19 个操作一次请求完成，包括配置 JSON 与 OPML 导入（单次事务、有大小上限）和阅读页图片本地化（带时限）。
- 状态：排队 → 运行 → 成功 / 失败。任务状态与业务结果分开：失败的任务也可能已有部分订阅提交成功。
- 容量：
  - 同时运行 2 个，排队 8 个；准入在任何副作用之前进行，满了直接拒绝，返回“服务器忙”。
  - 执行名额一直占到执行结束，与是否有人轮询无关。
  - 发起请求的客户端断开后，任务照常执行。
- 结果保留：
  - 从完成时起保留 10 分钟。
  - 最多保留 32 份结果，总共不超过 4 MiB。
  - 单份结果有字节上限，定义在 application 的公开结果类型里，客户端与服务器共用：
    - 可变长字段各有上限：订阅名 256 字节、地址 2 KiB、失败说明 1 KiB，超出部分截断并标明；
    - 刷新失败清单最多列 200 项，另给失败总数与“已截断”标记；
    - 序列化后的单份结果不超过 256 KiB；仍超出时，只保留计数与“明细过大、已省略”的最小形式。
    - 例外（评审 C3-R1 F07，2026-10-16）：WebDAV 下载的结果带当前设置，上限是设置的上限（自定义 CSS 最多 64 KiB，转义后最长六倍，约 400 KiB）；协议的 `MAX_JOB_STATUS_BYTES` 即此值。
  - 列表里的标题最多 512 个字符，超出的截断并以“…”结尾，在复制之前进行；两种存储规则相同（评审 C3-R1 F04）。原生存储用注册在每个连接上的 SQL 函数执行同一条 Rust 规则，不用 SQLite 的 `length`/`substr`（它们在第一个 NUL 处停止，评审 C3-R2 R2-01）。阅读页仍显示完整标题。
  - 订阅发现的结果按序列化后的字节数限额（含转义与页面地址），超出的候选不列出；页面地址超过 2 KiB、或没有可列出的候选时返回可纠正的错误（直接输入订阅源地址），不返回空的选择（评审 C3-R2 R2-02、R2-05）。
  - 解析网页时就受限（评审 C3-R3 R3-01、C3-R4、C3-R5、C3-R6）：网页按 4 KiB 分块读取，读到 head 结束、连续 32 KiB 没有读完任何标记（按块检查，读完的标记最长 40 KiB）、或读到的属性累计超过 16 384 个时停止，已读到的链接保留；字节顺序标记只由解码处去掉（各平台都在 `feed_body::read_feed_text` 解码正文时），发现阶段读到的 U+FEFF 是正文；最多收集 200 个不同的链接；超过 2 KiB 的链接在复制之前忽略，标题在复制之前截断；第一个 `<base href>` 生效，过长时只提供绝对地址的链接；解析后超过 2 KiB 的地址在复制与比较之前忽略，最多保留 50 个不同的候选。
  - feed 交给 feed-rs 之前检查结构（评审 C3-R5、C3-R6）：元素嵌套不超过 256 层、同时生效的 `xml:base` 不超过 16 个、`xml:base` 不超过 2 KiB、每个标签的属性（含读不了的）不超过 256 个；用 feed-rs 同版本、同设置的 quick-xml（`NsReader`）读，读不了即拒绝；属性按 feed-rs 的方式读（开着重复检查，跳过读不了的），两边看到同样的属性。
  - feed-rs 先建出整个模型再交给归一化，模型可达正文的数百倍。读取之前按元素估计（评审 C3-R6、C3-R7）：名字按最后一个冒号之后的部分认（与 feed-rs 相同）；Atom 文本结构（title、subtitle、summary、rights、content）里的元素 feed-rs 当作文本，不计；其余每个元素 256 字节，`item` / `entry` 再加 1 KiB，元素与它的每个属性再各加生效基地址的长度（按 feed-rs 的方式解析并序列化，含百分号编码与国际化域名）；媒体评级按它被复制进的每个内容（同一条目或 `media:group` 里在它之前的 `media:content` 与 RSS `enclosure`）计 64 字节加它的字节数（未识别的实体引用连同 `&` 与 `;` 计，feed-rs 原样保留它们），一个媒体对象最多 16 个评级；`media:content` 自己的评级不会被复制，不计也不占名额。JSON Feed 每个对象 2 KiB、每个不是键的字符串 256 字节，每个条目再计一遍 feed 级作者（feed-rs 把它们复制进没有作者的条目），键按 serde 的方式解码后比较，一个作者列表最多 64 个作者；serde 也接受把对象写成字段的数组，根、条目、作者处出现数组即拒绝（JSON Feed 本就要求对象），嵌套最多 128 层（本程序的上限，未知字段也算：serde_json 跳过未知字段时不限深度，扩展字段嵌套更深的 feed，feed-rs 读得了、这里会拒绝）。估计超过 64 MiB 即拒绝。8 MiB 的大播客、全文 Atom、JSON Feed 实测峰值 30、27、16 MiB；预算内各类大输入实测的最坏峰值是 100 MiB（空 `media:group`）。估计不是证明过的内存上界（修复前 8 MiB 的空条目约 1 GB，长基地址下的链接约 3 GB）。会被拒绝的还有：数万个条目、每个只有少量文字的 feed；带大量空扩展元素的 XML feed（扩展元素同样按元素计费）；内容已各带评级、条目或分组又有评级的媒体集合（这个评级仍按之前所有内容计费）；同一个作者列表里超过 64 个作者对象（重复的、没有名字的也算）；feed 级作者多或长、条目又多的 JSON Feed（即使条目各有作者，也按每个条目复制一遍 feed 级作者计费）；JSON 扩展字段里的大量对象（扩展字段同样计费）；没有声明 Atom 命名空间的 Atom 文档里的大量 XHTML 元素（feed-rs 补上的默认命名空间这里不认）；RSS 正文（如 `content:encoded`）里没有转义、直接写成元素的大量标签（只有 Atom 文本结构不计元素）；JSON 扩展字段里的大量字符串（字符串同样计费）；feed 级作者里 feed-rs 不用的长字段（也按每个条目继承计费）；RSS 2.0 与 0.9x 频道结束之后的内容（feed-rs 读完频道就返回，预检仍读完整个文档，那里的超限或语法错误照样拒绝）（评审 C3-R11）。本机同时只解析一个 feed（进程级名额）；添加订阅时只有解析 feed 那一步占名额，网页发现不占。
  - 估计按 feed-rs 2.4.0 的实现（工作区固定为 `=2.4.0`）：逐一读过它的解析器里每个循环与复制，比正文增长更快的只有 JSON Feed 的作者继承与作者比较、Media RSS 的评级传播（传播进 `media:content` 与 RSS `enclosure`），都已计入或限制；serde 的位置写法与时间解析的 panic 见下。估计还假定 feed-rs 按元素的实际嵌套来读：它在 RSS 文本处理中吞掉无效字符引用的错误，之后按错位的层级读元素（RSS 频道标题里 Atom 文本结构中的条目被当成频道条目），所以字符数据里（含 Atom 文本结构内部）出现 quick-xml 无法解析的字符引用（如 `&#0;`）都在读取前拒绝（评审 C3-R9）；属性值里的无效引用 feed-rs 保留原文、不影响遍历，照常接受；这也不是完整的 XML 合法性检查，`&#1;` 这样能解析的照常接受（评审 C3-R10）。文档在元素内部结束（截断）时，feed-rs 仍读到结尾，把最后一段文字交给其中的评级并复制进之前的内容，之后才报缺结束标签，所以没有结束的评级在结尾照样计费；只缺根元素结束标签的 RSS 2.0 与 0.9x feed，feed-rs 读完频道就返回、读得了，这里也照常接受（Atom 与 RSS 1.0 这样的文档 feed-rs 照样报错）（评审 C3-R10、C3-R11）。估计对命名空间不加区分（任何命名空间里名为 `rating`、`content` 的元素都按媒体元素计），宁可多计；时长与媒体时间的检查也一样（任何命名空间里名为 `duration` 的元素、名为 `thumbnail` 的 `time` 与名为 `text` 的 `start` / `end`，即使 feed-rs 不读，数字过长也拒绝，评审 C3-R11）。
  - feed-rs 解析 iTunes 时长、`media:thumbnail` 的 `time`、`media:text` 的 `start` / `end` 时，遇到放不下的数字会 panic（`parse_npt`）：其中含非 ASCII 数字、或一段超过 12 位数字的 feed 在读取之前拒绝。原生端 feed-rs 内的任何 panic 都转为解析失败；wasm 遇到 panic 直接中止，靠前面的检查（评审 C3-R8）。换版本前要重读；换成只建归一化所需字段的解析器是 C3 之后的设计项。
  - 工作区用 quick-xml 0.41：它的重复属性检查有哈希预筛，但哈希密钥固定，真正的重复或预先算好的碰撞都会线性扫描该标签此前的属性名，所以属性数要设上限（OPML 同样）；标签长度不设上限（第四轮后加的 16 KiB 上限已撤销，它还让自己导出的长标题 OPML 无法再导入）。
    - 截断在构造结果时就进行，不先构造完整结果再裁剪。
  - 测试：保留区为空时，一份超大的结果按上述规则变小。
  - 超出时先淘汰最早完成的结果，被淘汰的结果再被轮询时返回“状态不可用”。保留期因此是上限而不是保证，饱和测试覆盖这一点。
- 任务 id 为 128 位随机值，重启前后撞号的概率可以忽略。
- 轮询：单次最多等待 10 秒（这只是单次请求的时限，不限制任务本身的运行时长），返回后客户端按退避继续。重启后或结果被淘汰后返回“状态不可用”。

**结果未知**：
- `ErrorCode` 新增“结果未知”。`HttpBackend` 在以下情况返回它：
  - 写请求已发出却没收到回包（断线、超时、连接被重置），包括没拿到任务 id 的任务创建；
  - 任务已被接受（拿到了任务 id），但最终结果丢失：轮询得到“状态不可用”。
- 界面运行时统一处理，与后端无关：显示“结果未知”，然后重新读取受影响的状态。重新读取的结果不当作这次命令成败的证明，不显示为“已成功”。
- 写请求一律不自动重发，包括会替换本地配置的 WebDAV 下载。只读的轮询可以按退避重试。

**上限与批量已读**：
- 列表查询有条数上限。
- 批量已读的预览与确认都在各自的事务里、同一个快照上，用与选择完全相同的条件（含“未读”）取未读 id，至多取到上限加一个（一次查询，不另行计数）。超过上限（10 000 篇）就返回“范围过大，请缩小筛选”的错误，不再继续取。
  - 确认时新选择集超限也一样，返回这个错误而不是整份 `SelectionChanged`。
  - 不截断、不分批，保持“完整集合比较、一次提交”（B2）。
  - 确认请求的体积上限按预览上限设定；伪造的小预览遇上大选择集，同样在计数阶段被拒绝。
- 配置 JSON 与 OPML 导入、请求体、并发都有上限。

**构建标识**：
- 服务器与网页包在构建时嵌入同一个构建标识：发布构建用发布 tag，开发构建用 `dev-<提交>`，工作区有未提交改动时为 `dev-<提交>-dirty-<内容哈希>`。不用 `CARGO_PKG_VERSION`，它长期停在 0.1.0。
- `/api/v1` 的应用路由要求请求头 `X-RSSR-Build`：缺失或不一致时拒绝一切写请求（含任务创建），读请求照常。认证路由（登录、退出、`/api/v1/session`）不检查构建标识，靠上面的 Origin 规则保护。
- 页面收到不一致的错误时提示重新加载，并保留正在编辑的内容（设置草稿、CSS）。

**验收归属**：
- 本步用原始 HTTP 请求做服务器侧的契约测试：每个路由与独立的 `LocalBackend` 夹具对照结果；任务的准入、名额、保留、淘汰、重启与 id；批量已读上限（含确认时超限与伪造预览）；构建标识不一致。
- 依赖客户端的部分移到 C4 验收：结果未知、草稿保留、重新加载提示。

### C3 与 C5 服务器部分的实施细节（2026-10-16）

**放置**（依赖方向不变：rssr-web → rssr-api / rssr-infra → rssr-application → rssr-domain）：
- `rssr-api` 新增协议模块，只有数据、不依赖 HTTP 库，服务器与 C4 的 `HttpBackend` 共用：

  - 任务类型：任务 id、任务种类、状态（排队 / 运行 / 成功 / 失败）与各种结果；
  - 错误码补上协议层的几种：未登录、来源不受信任、CSRF 不符、构建标识不符、请求过大、状态不可用（任务结果已淘汰或服务器重启过）。C2 里 `/api` 的临时错误码统一到这里；繁忙与超时沿用 `unavailable`。
- `rssr-application`（各平台一致）：
  - 刷新结果的字节上限在构造时截断；
  - 文章列表一次最多 2000 篇（Develata 2026-10-16 确定），`EntriesListOutcome` 带“已截断”，列表页提示“只显示最新的 2000 篇，请用筛选或搜索缩小范围”；
  - 批量已读的上限是 10 000 篇，存储实现至多读到上限加一个 id，超出就返回“范围过大”。浏览器存储与原生存储都执行；用例层另外拒绝 id 多于上限的确认（不可能来自真实的预览）。
- `rssr-infra`：`LocalBackend` 构造结果时套用上限；定时刷新的调度（C5）改为每 60 秒重读设置，刷新经 `RefreshFlight` 在后台进行，调度器不等它结束。桌面与 Android 共用同一个循环。
- `rssr-web`：
  - 打开数据目录里的资料库，用 `ensure_server_policy` 与 `native_local_backend_with` 建立后端，并启动定时刷新；
  - `api` 模块：路由、构建标识检查、请求 id、请求体与并发上限，处理函数只经 `Backend` 调用；
  - `jobs` 模块：后台任务。
- 构建标识：仓库内一份共用的构建脚本片段，rssr-web（C3）与 rssr-app（C4）的 `build.rs` 都引用它，保证算法相同。
  - 优先取环境变量 `RSSR_BUILD_ID`（发布与镜像传入）；
  - 否则从 Git 得到 `dev-<提交>`，工作区有改动时为 `dev-<提交>-dirty-<内容哈希>`；
  - 没有 Git 时为 `dev-unknown`。镜像构建时 `.dockerignore` 排除了 Git 元数据，C6 必须给两者传入同一个 `RSSR_BUILD_ID`：否则两者都是 `dev-unknown`，不同版本的镜像彼此认不出，过期页面的写入防护失效（C4 设计评审 S8 更正：此前写“对不上、写请求全被拒绝”不对）。

| 文章列表 | `GET /api/v1/entries?query=<JSON>` |

条件复杂的读操作把 JSON 放在查询参数里，仍是 `GET`。

**上限**：
- 请求体默认 64 KiB，配置 JSON 与 OPML 导入 4 MiB。另有两处由领域上限推出（实施时补，2026-10-16）：
  - 改设置 400 KiB：自定义 CSS 最多 64 KiB，JSON 转义后最长六倍；
  - 批量已读的确认 256 KiB：10 000 个 id（每个连逗号至多 20 字节）加预览时不超过 4 KiB 的查询。
- 同步路由同时最多 32 个，超出返回“繁忙”；导入同时只有 1 个。每个操作在自己的任务里运行并持有名额到结束：客户端断开既不会让写入半途取消，也不会提前释放名额；
- 阅读页图片本地化的现有时限最长 245 秒（24 张图，每张 10 秒，另加 5 秒），对同步请求太长：路由另设 60 秒总时限，到时返回“暂时不可用”并说明结果未知。下载被取消；最后一次写回是单次比较后写入，若时限正落在它上面仍可能提交，正文因此要么不变、要么整体换成本地化版本，不会混合（评审 C3-R1 F06 修正了“正文不变”的说法）。
- 名额在读取请求体之前取得，请求体须在 60 秒内收完，所以正在接收的请求体也受名额约束；不收请求体的写请求拒绝带来的请求体；同一个查询参数出现两次时拒绝（评审 C3-R1 F03、F13）。
- 带 JSON 查询参数的 `GET` 限制参数长度（4 KiB），超出返回“请求过大”；参数解析失败返回“输入无效”。所有 `/api` 错误都是统一的错误体。

**线上形式**（`rssr-api::protocol` 的模块文档为准，C4 的 `HttpBackend` 照此实现）：
- 写请求的请求体是对应请求类型的 JSON；批量已读的确认直接是 `MarkReadPreview`。
- 成功一律 `200` 加结果的 JSON；没有结果的操作回答 `null`；两种导出把文档作为 JSON 字符串返回。
- 应用路由的每个回答带 `X-RSSR-Request-Id`，错误体里的 `request_id` 与它相同；回答一律不缓存。
- 已知路径上的错误方法与不存在的接口一样回答 JSON 404；会话检查包住这种回退，未登录时先得到 401。
- 创建任务回答 `202` 与任务 id；轮询回答 `200` 与任务状态。`wait_ms` 是普通整数，缺省为 0，超过 10 000 按 10 000 计；格式不对的 id 与未知、过期、被淘汰、重启前的 id 一样回答“状态不可用”（410）。轮询不占同步操作的名额（它只等待），但同时最多 64 个，超出返回“繁忙”（评审 C3-R1 F10）。
- `/api` 下的每个回答都带请求 id，包括认证层的拒绝与方法回退（评审 C3-R1 F14）。日志只记请求 id 与错误码，不记错误消息（消息可能引用带凭据的订阅地址，F05）。

**提交顺序**（每步单独验证）：
1. 协议（`rssr-api`）与错误码统一；
2. 应用层上限（结果截断、列表 2000、批量已读 10 000，含列表页提示）；
3. 服务器同步 API（资料库、后端、构建标识、请求 id、上限）与原始 HTTP 契约测试（与独立的 `LocalBackend` 夹具对照）；
4. 后台任务及其测试（准入、名额、保留、淘汰、重启、id）；
5. 定时刷新调度（C5）与受控时钟测试；
6. 文档与交接记录，然后送独立评审。

### C4 的实施设计（2026-10-19，Develata 确认的决定；第一轮设计评审后修订）

**已确认的决定**（Develata，2026-10-19）：
- `HttpBackend` 放在 `rssr-infra`，由默认关闭的 `http-backend` feature 控制（与计划“`rssr-app` 新增”不同：rssr-app 与 rssr-web 都是二进制 crate，放在 rssr-app 时没有原生测试能让它连真实服务器；独立 Codex 设计咨询推荐此方案，排序 B > A（新 crate）> C）。
- 浏览器存储由 `rssr-infra` 的 `browser-store` feature 控制，只有演示站（`pages-demo`）打开；正式 Web 构建不含这段代码。
- 版本不一致时，设置页的草稿（含自定义 CSS）存进本标签页的 `sessionStorage`，提示重新加载；重新加载后恢复一次再清除。
- C4 分步实施、分别评审、一起合并（中间不推送）。原定两步；第一轮设计评审指出界面恢复行为需要一套明确的契约，现细化为三步：C4a 协议、传输与服务器；C4b 界面的恢复行为；C4c 真实服务器上的浏览器回归、CI 与文档。

**分工原则**：传输编码、CSRF 缓存、任务轮询与错误分类在 `rssr-infra::http_backend`；跳转、提示、草稿存储与刷新协调在 `rssr-app`。不新增 crate，不做持久的任务回执、通用重试框架或离线库。

#### C4a 协议、传输与服务器

1. 结果未知是协议的一部分（评审 C4D-R1 B1）：`ErrorCode::OutcomeUnknown`（线上 `outcome_unknown`，HTTP 504）。客户端在下述情况自行产生；服务器在操作可能已经提交、却无法确认时返回它——目前是阅读页图片本地化超过时限（最后一次写回可能落在时限上），原来的 `unavailable` 改为它；准入阶段的“繁忙”仍是 `unavailable`，那时操作没有运行。另加 `protocol::Session { csrf_token }`，服务器的 `/api/v1/session` 用它构造。
2. feature 与依赖：
   - `rssr-infra`：`browser-store = []` 门控 wasm 上只有浏览器内 `LocalBackend` 用到的部分（`application_adapters::browser`、`compose_browser_use_cases`、订阅探测的 wasm 实现；确切范围以正式 Web 不开它时能编译为准；通用的 `LocalBackend` 与共享的 HTML 处理不受影响）；`http-backend = []` 门控 `http_backend` 模块，wasm 上另加 `gloo-timers`（已在锁文件里）。
   - `rssr-app` 的 wasm 依赖开 `rssr-infra/http-backend`；`pages-demo = ["rssr-infra/browser-store"]`；`WebHost`、`BrowserClock` 及其构造只在 `pages-demo` 下编译。演示站构建两个 feature 都有、启动时选 `LocalBackend`；正式 Web 只有 `http-backend`、选 `HttpBackend`。
   - `rssr-web` 的 dev-dependency 开 `rssr-infra/http-backend`。
   - 三个 wasm 契约 harness 声明 `required-features = ["browser-store"]`；改的是 `scripts/wasm_contract_runner.rs` 里拼 cargo 参数的代码及其测试（含预构建 harness 包的准备），不只是 shell 脚本（评审 S5）。
   - 依赖图门禁：按包、目标与 feature 分别调用 `cargo tree -e features`，打印解析出的 feature：正式 Web（`-p rssr-app --target wasm32`、默认 feature）的 `rssr-infra` 没有 `browser-store`、有 `http-backend`、不含 SQLite；演示站（`--features pages-demo`）两者都有。feature 只说明“有没有”，选了哪个后端另由启动代码的编译与 C4c 的真实服务器回归证明。不禁止浏览器存储 API 本身：设备偏好与草稿仍合法使用 `localStorage` / `sessionStorage`。
3. `rssr_infra::http_backend::HttpBackend`（原生与 wasm 共用一份实现）：
   - 构造参数：服务器地址、构建标识（由入口 crate 在构建时算出后传入）、配置好的 `reqwest::Client`。原生客户端明确关闭自动重试（`retry::never()`）与重定向；浏览器用 fetch 的默认同源凭据。
   - 每个请求带 `X-RSSR-Build`，写请求带 `X-RSSR-CSRF`。令牌第一次写之前从 `/api/v1/session` 取得并缓存；回答 `csrf_mismatch` 时重取一次、重发一次（服务器在应用处理之前拒绝，已核对 `auth.rs`）。取令牌时得到本协议的错误（如 `unauthenticated`、`unavailable`）照原样返回；只有传输或解码失败才是 `network`，那时写请求没有发出（第二轮设计评审 R2-01）。
   - 结果未知的判定按目标区分（评审 S4）：原生客户端能分辨“连接没建立”（请求未发出，`network`）；浏览器的 fetch 失败不区分阶段，写请求一旦开始 fetch，失败一律 `OutcomeUnknown`。两端共同的：写请求已发出而没有收到完整、可解析的本协议回答（超时、连接中断、回答体读不完或解析失败、HTML 错误页等非本协议的回答）都是 `OutcomeUnknown`；读请求的同样情况是 `network`。写请求一律不自动重发（CSRF 那一次除外）。服务器的 `/api` 从不以重定向回答（过期会话是 JSON 401，已核对）；部署时反向代理也不得重定向 `/api` 的写请求，C4c 验证。
   - 后台任务：创建得到 `JobCreated`，拿不到可解析的任务 id 即结果未知。轮询 `wait_ms=10000`；轮询请求本身的失败（网络、`unavailable` 繁忙、非本协议回答）在第一次失败后最多重试 5 次，间隔依次 1、2、4、8、16 秒，连续第 6 次失败即结果未知；任何一次成功的轮询把计数清零（R2-06）；任务终态里的 `Failed { error }` 照原样返回（含它自己的 `unavailable`），不与轮询失败混淆；`status_unavailable` 即结果未知；轮询得到 `unauthenticated` 时任务已被接受，返回结果未知，并以类型化的原因注明需要重新登录：`BackendError` 增加可选字段 `reason`（线上缺省为空，只在 `outcome_unknown` 上使用，目前唯一取值 `unauthenticated`），界面据此处理而不解析消息（R2-01）。总时长不设上限，由界面的取消结束等待；客户端停止等待不取消服务器上的任务。
   - 请求时限：普通请求 30 秒，长轮询 20 秒，图片本地化 70 秒（服务器 60 秒）；wasm 的 reqwest 以 `AbortController` 实现时限（已核对锁定源码）。
   - 回答的上限（实施时由代码评审 C4A-02、C4A-R2-02 补入）：`rssr-api::protocol` 的 `MAX_ANSWER_BYTES`（64 MiB）、`MAX_JOB_STATUS_BYTES`（轮询）、`MAX_SMALL_ANSWER_BYTES`（64 KiB：取令牌、任务创建与错误回答）。服务器不发超过上限的回答：读请求 `too_large`，写请求（已执行）`outcome_unknown`；错误消息截短到 1 KiB。客户端边收边数解码后的字节，超过即放弃：读请求 `network`，写请求结果未知。
   - `ensure_auto_refresh_started` 是空操作。
4. 服务器（`rssr-web`）：
   - 删除 `/feed-proxy`（路由、`proxy` 模块与其隔离测试夹具）。原生测试断言：已登录时 `GET /feed-proxy?url=…` 得到 404、没有发出任何上游请求；未登录时与其他页面路径一样重定向到登录页。原来的“上游文档不能执行脚本”由 C4c 的阅读页恶意正文浏览器测试承担（评审 S7）。

   - 图片本地化超时改回答 `OutcomeUnknown`，测试覆盖“时限落在写回上”。
5. 网页端的最小切换：非演示站构建 `HttpBackend`，地址取页面的 origin；构建标识来自 `rssr-app/build.rs`（引用 `build-support/build_id.rs`，放在非 Windows 提前返回之前）。删除本地浏览器门禁（`localStorage` 口令与门禁 cookie 探测）；页面在服务器登录之后才下发，界面不再有门禁，演示站照旧直接进入。
6. 同一步里改写依赖被删接口的可执行代码，或明确交给 C4c（评审 S6）：

#### C4b 界面的恢复行为

1. 错误按类型传到页面（评审 B2）：界面命令不再在运行时里把 `BackendError` 变成字符串，而是带着错误码交给页面；共用一个分类：`outcome_unknown` → 提示“结果未知”（不是“失败”），释放进行中的标记、保留草稿，并让受影响的状态只读刷新；`unauthenticated` → 跳转 `/login?next=<当前路径>`（草稿按下面第 4 条保存）；`build_mismatch` → 全局提示“页面版本与服务器不一致”与重新加载按钮；其余照旧显示“……失败”。重新读取的结果只更新显示，不当作这次命令成功的证明。测试用可控的假后端逐类断言页面状态（原生，界面特征测试用的 `LocalBackend` 覆盖不到这些分支）。
2. 只读刷新的契约（评审 B3、S1）：每个页面（外壳设置、文章列表、订阅、设置、阅读页）有一条只读刷新路径：
   - 只读，从不安排写操作：阅读页刷新保留“已请求图片本地化”的标记与阅读位置，不替换正在看的正文；
   - 合并同时到来的触发，丢弃被更新的读取超越的旧结果（读取代号）；写操作的结果确立了更新的状态时，作废还在途的读取，保留设置页已有的写入顺序保护（例如外壳的设置读取晚于一次保存才回来，不得把外观改回旧值，R2-03）；
   - 保留正在编辑的内容；底层快照变化时让等待确认的破坏性操作（配置导入、批量已读）失效并要求重新确认；
   - 触发：页面重新可见、窗口获得焦点、重新联网、任务终态（成功或失败都可能已提交一部分）、结果未知。`online` 事件不证明服务器已恢复，刷新失败时照常显示错误。
3. 后台任务归应用所有（评审 S2）：任务型命令（刷新全部、刷新单个、添加订阅、WebDAV 上传、下载）不再在页面组件的任务里轮询，而在应用级的任务里（沿用外壳已有的任务归属）一直轮询到终态；提示与刷新经全局信号发出，与表单相关的结果（清空输入、释放进行中的标记、订阅发现的候选）带操作令牌，只交给发起它的那次操作与页面实例，不落到之后新开的同一页面上（R2-02）；页面离开不取消轮询，应用关闭时停止等待。重新加载页面会丢失任务 id：之后只做普通的启动读取，不重建任务，也不说这些读取证明了任务的结果。轮询中得到未登录时，提示重新登录并说明该操作结果未知。
4. 草稿跨重新加载保留（评审 S3）：存入 `sessionStorage` 的是带版本号的“已提交的修改加其后的待提交修改”（不是整份设置，以免覆盖别处的修改），在点击重新加载（或跳转登录）时取最新的；重新加载后先读服务器的设置，再把草稿作为待保存的修改覆盖上去，不自动保存，恢复后清除；`sessionStorage` 写不进时不重新加载，页面与草稿原样保留，并提示暂时无法保留草稿；提示旁另有明确写着“草稿会丢失”的“仍然重新加载 / 仍然去登录”（实施时补入，第二部分第一轮评审认可）。
5. 启动与读取失败可见（评审 S9）：外壳初始化读取失败时显示原因与“重试”（只读刷新外壳与当前页），不静默使用默认设置。连接恢复与资源就绪分开：任一请求成功只清除“连接中断”一类的提示，设置初始化的错误与重试一直保留到设置真正读到（R2-04）。开发时的同源方案（`rssr-web` 托管 `dx` 构建的包）写入文档。

#### C4c 浏览器回归、CI 与文档

1. 真实服务器加夹具资料库的浏览器回归，替换 CI 的 `web-ui` 任务（Python 静态服务器加 `localStorage` 夹具）；`run_rssr_web_browser_feed_smoke.sh` 改用独立的 feed 夹具服务与出站例外。
2. 浏览器验收（评审 V1）：经部署 origin 与反向代理的真实 cookie、Origin 与 CSRF；fetch 的失败、中止与重定向（反向代理不重定向 `/api` 写请求）；后台标签页的时限；任务进行中切换页面、整页重新加载丢失任务 id、任务完成更新当前页面；草稿与 CSS 恢复、恢复后的再编辑、存储不可用、只恢复一次；正式 Web 选用 `HttpBackend`、演示站网络被禁用、浏览器不再自行定时刷新；阅读页恶意正文不能执行脚本（承担原 `feed-proxy-isolation` 的覆盖）；焦点、可见与联网事件交叠时的读取（合并为一次只读刷新，零写入，含文章页的偏好保存；触发经 `document::eval` 的监听进入外壳，原生测试覆盖不到；请求计数在各触发引起的全部效果落定之后再数）；阅读页 HTML 文章读取失败后经刷新恢复（恢复加载不请求图片本地化）；启动读取失败之后设置页的恢复（不再次启动周期刷新）；恢复的草稿紧接着遇到重新登录（C4b 第二部分第一轮评审补入）；跳转登录或重新加载被用户停下之后再打开设置页，草稿只恢复一次（第三轮补入）；两个浏览器之间的修改互相可见。
3. 构建标识（评审 S8）：C4c 用同一对页面与服务器产物做一次写请求；C6 给两者注入同一个明确的 `RSSR_BUILD_ID`（发布不能是 `dev-unknown`；只设 `RELEASE_TAG` 不够），并测试旧页面对新服务器。
4. 文档：README（中英）、用户指南、部署文档、`CLAUDE.md`、`AGENTS.md`、`crates/rssr-app/src/bootstrap/web/AGENTS.md`、测试文档与 specs 中关于 `localStorage`、Web Locks、`/feed-proxy`、本地门禁的描述，以及从旧版 Web 升级时文章不迁移、不再离线可读的说明。

要用实际效果断言的恢复不变式（R2-07；C4a、C4b 用受控测试按各自的层断言，界面渲染与浏览器里的请求计数在 C4c）：
- 结果未知的写操作之后成功的重新读取：没有成功回执，没有第二次写；
- 焦点、可见、联网触发的刷新：零写入（包括文章页由界面状态触发的工作区偏好保存）；
- 离开页面又回来之后任务才完成：不改动无关的草稿与进行中的标记；
- 应用销毁：轮询请求与退避计时停止；
- 版本不一致：重新加载提示出现，已提交与之后的修改都保留，恢复后不自动保存；
- 成功回答的内容格式不对、任务终态的结果种类不对：不编造成功。
- 失败与结果未知看得见（C4b 第一部分的评审 C4B-A-R3、R4 补入）：各页（文章列表、订阅、设置、阅读页）的状态条显示失败与结果未知；导航展开与收起时，手动刷新的结果都有标记（阅读页的 Home 按钮、收起时的折叠按钮）；解析启动页失败时，页面之上的提示在跳转到全部文章之后仍在，可关闭；外壳读取设置失败的提示与“重试”。

C4c 的浏览器验收与 C4a、C4b 一起作为合并门槛。

### C5 服务器运行与维护

- `rssr-web` 打开数据目录（`--data-dir` / `RSSR_DATA_DIR`，容器内 `/data`）里的 `library.sqlite3`，经 `LocalBackend` 调用用例。服务器端的 host 与原生相同（含图片本地化），出站策略来自 `outbound.json`。
- 唯一的定时刷新任务，不依赖浏览器在线：
  - 设置每 60 秒重读一次，与刷新间隔无关。
  - 刷新经 `RefreshFlight` 在后台进行，调度器不等它结束，因此刷新进行中也能看到新设置。看到新的间隔不取消正在进行的刷新，但下一次刷新按新间隔安排。
  - 调度器自己开始的刷新同时最多一个：上一次还在进行时到期的那次不开始、也不排队等待，上一次结束后的第一次检查时开始（评审 C3-R1 F11）。
  - 服务器启动顺序（评审 C3-R1 F01、F02、F12）：数据目录不存在时先以 0700 创建；进程 umask 为 077，资料库与伴随文件在打开前后都改为仅所有者可读写；资料库在认证库开始运行之前打开；定时刷新在取得服务器排他锁之后才开始。
  - 用受控时钟测试：长间隔改短；刷新进行中 CLI 改设置，60 秒内被看到。
- 备份（`rssr-cli backup <文件>.sqlite3`，单独一个提交；下面是计划时的写法，实施中的改变——专属线程上的独立连接、目标名限定为 `*.sqlite3`、每个目标一个临时目录 `<目标>.partial`——见交接记录“C5 备份与恢复”一节）：
  - infra 提供在事务之外运行的维护操作，带时限（默认 10 分钟，到时中断语句），并可取消（Ctrl-C）。
  - 对同一目标的备份互斥：先取 `<目标>.lock` 上的咨询锁，有限时间内等不到就报错。清理、写入与发布都在持锁期间进行。
  - 持锁后，先清除本协议留下的临时文件（实施为临时目录 `<目标>.partial` 里名为 `partial-<随机>` 的条目；只可能来自已崩溃的备份，正在进行的那个会持有锁）。
  - 用“仅在不存在时创建”新建临时文件 `<目标>.partial/partial-<随机>`（SQLite 允许写入空文件），`VACUUM INTO` 写入，同步到磁盘。
  - 发布用“不替换”的方式：建立硬链接到目标名，目标已存在时这一步原子失败；然后删除临时文件，并同步目录。文件系统不支持硬链接时明确报错，不退回会覆盖目标的改名。
  - 失败时删除临时文件。
  - 前提（Develata 2026-10-19，第五轮评审之后）：目标所在目录只由运行备份的用户掌控，其中没有刻意制造的别名（硬链接、符号链接、挂载）。能查到的几种别名会被拒绝，但这只是保险；前提之外的情形是已知限制，不作为评审的阻断项。
  - 验收：并发写入时得到一致副本；目标已存在时拒绝；同一目标的两个备份同时进行；中途被强杀后重启清理；在实际支持的文件系统（容器内的数据卷）上测试。
- 恢复（写入部署文档）：
  1. 停止服务器与所有 CLI，确认没有进程打开资料库。
  2. 把旧的 `library.sqlite3` 与 `-wal`、`-shm` 一起移走，再放入备份。
  3. 重新放置 `outbound.json`。
  4. 两条路：
     - 已有 `auth.sqlite3`：运行 `rssr-web sessions revoke-all`，保留凭据、吊销全部会话；
     - 新主机、没有 `auth.sqlite3`：按 Q1 的顺序有意地提供当前凭据。
  5. 启动服务器。

### C6 部署、镜像与迁移

- 发布产物的命名（Develata，2026-10-20）：服务器模式按主机平台发布“服务加页面”的一个包，与 `rssr-cli-<平台>` 对齐：`rssr-web-linux-x86_64.tar.gz`、`rssr-web-windows-x86_64.zip`、`rssr-web-macos-x86_64.tar.gz`、`rssr-web-macos-aarch64.tar.gz`，各含 `rssr-web` 程序与 `public/` 页面，两者同一次构建、构建标识一致。镜像用 linux 版的同一构建。不再发布只有页面的 `RSS-Reader-web.tar.gz`（C4a 之后页面离开服务用不了）。演示站照旧单独构建（`pages-demo`，后端在编译时选定，正式页面里没有浏览器存储），静态部署到 GitHub Pages，不作为发布产物。文档里区分“页面”（浏览器里的界面）与“`rssr-web` 服务”（主机上的进程，附带页面）。

## 已确认的决定（Develata，2026-10-15）

- **Q1 所有者凭据**：首次启动时由现有配置建立凭据（顺序见 C2，含旧认证状态文件），此后以 `auth.sqlite3` 为准；改密码用 `rssr-web passwd`。旧部署升级时凭据相关的环境变量不用改（新增的公开来源设置另需填写，见 C2）。
- **Q2 后台任务**：刷新全部、刷新单个订阅、添加订阅（含首次刷新）、WebDAV 上传与下载走后台任务；配置 JSON 与 OPML 导入同步执行；阅读页的图片本地化同步执行、带时限。
- **Q3 CLI 的出站策略**：由数据目录里的 `outbound.json` 决定。存在时服务器与 CLI 都执行 `PublicOnly`；确实不存在时为 `Unrestricted`；其他情况报错，不放宽（见 C1）。
- **Q4 会话**：不做设备记录与会话面板（与功能设计哲学不符）。登录后由持久 cookie 自动记住，使用时自动续期；30 天未使用过期，另有 180 天的绝对上限。退出登录吊销本会话，改密码吊销全部会话，都不需要界面。通行密钥（WebAuthn）暂不做，以后可以加，不改变会话设计。
