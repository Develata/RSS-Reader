# v0.2 阶段 C：服务器端 Web（实施计划）

依据：[v0.2 架构](./v0.2-architecture.md)（目标 1、API、安全与运行、阶段与门禁）。本文把阶段 C 拆成可独立验收的工作项，写明现状、做法与决定。

- 四个决定（Q1–Q4）已由 Develata 确认（2026-10-15，见文末）。
- 第一版计划经独立设计评审（Codex，FAIL：1 个阻断、8 个应修、6 个待核实），本版逐条吸收，不改动已确认的决定，只把它们写精确。

## 现状（2026-10-15 调查）

- `rssr-web` 目前只是静态包托管加登录：
  - 认证：用户名来自环境变量。Argon2 哈希来自环境变量，或来自首次启动时写入认证状态文件（默认 `$HOME/.rssr-web-auth.json`，容器内 `/app/auth/auth.json`）的哈希；部署文档允许初始化后删除密码环境变量。
  - 会话：cookie 是 HMAC 签名的“用户名:到期时间”，服务器不保存会话，退出登录无法吊销已复制的令牌，默认 12 小时。
  - 退出登录是 `GET /logout`；没有 CSRF 与 Origin 校验。登录有失败限速。
  - `/__codex/*` 冒烟辅助路由在开启时会给任何人发会话 cookie（默认关闭）；`scripts/run_rssr_web_browser_feed_smoke.sh` 依赖它。
- 资料库在每个访客浏览器的 `localStorage` 里；`/feed-proxy` 代抓 feed 以绕过 CORS，CI 的 `feed-proxy-isolation` 任务测试它。
- 出站访问：只有 `/feed-proxy` 检查目标地址，并固定 DNS 结果、逐跳复核重定向、禁用环境代理。
  - 它拦截私有、回环、链路本地、共享地址、基准测试、文档、组播、0/8 与 240/4 等，以及这些地址的 IPv4 映射形式。
  - 漏掉了 `192.0.0.0/24`、NAT64 前缀（`64:ff9b::/96`、`64:ff9b:1::/48`）、6to4（`2002::/16`）、Teredo（`2001::/32`）与已废弃的 IPv4 兼容形式，所以不能原样复用。
  - infra 里的 feed 抓取、订阅发现、图片本地化、WebDAV 没有地址检查（适合桌面，不适合服务器），但各有自己的重定向、认证、降级与 Referer 规则。
- `Backend` 有 24 个异步操作，外加一个同步的生命周期钩子 `ensure_auto_refresh_started`。只有 `LocalBackend` 一个实现；公开类型已可序列化（B2-D7）。
- 本地化的图片以 `data:` URI 写进正文 HTML、存在库里，服务器端可照搬原生做法。
- 自动刷新读一次设置后睡满剩余间隔（最长可达一年），睡眠期间看不到 CLI 改的间隔。
- 存储执行器把每个任务包在事务里，`VACUUM INTO` 不能在其中运行。

## 工作项

### C1 出站访问策略（infra）

所有出站请求（feed 抓取、订阅发现、图片本地化、WebDAV）共用一层地址策略：

- `Unrestricted`：桌面、Android 与普通 CLI 用，保持现状。
- `PublicOnly { allow }`：服务器用。只允许全局可路由的单播地址，管理员可在策略文件里显式放行地址段或主机名。

地址判定按 IANA 特殊用途地址登记重写，测试先行：
- IPv4 拒绝：
  - `0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`、`172.16/12`、`192.0.0/24`、`192.0.2/24`；
  - `192.88.99/24`、`192.168/16`、`198.18/15`、`198.51.100/24`、`203.0.113/24`；
  - `224/4`、`240/4`、`255.255.255.255`。
- IPv6 只接受 `2000::/3` 内的地址，并拒绝其中的：
  - 文档 `2001:db8::/32`、IETF 协议分配 `2001::/23`（含 Teredo `2001::/32`）、6to4 `2002::/16`、NAT64 `64:ff9b::/96` 与 `64:ff9b:1::/48`；
  - 已废弃的 IPv4 兼容 `::/96` 与站点本地 `fec0::/10`。
  - IPv4 映射形式按内嵌的 IPv4 判定。
- 用例覆盖字面地址、DNS 应答与重定向目标三种入口，以及映射、兼容、NAT64、6to4、Teredo 各形式。

传输层要求：
- `PublicOnly` 的客户端禁用环境代理（否则代理替我们解析并连接，地址检查失效），客户端构建失败就失败，不回退到默认客户端。
- 地址检查放在自定义 DNS 解析器里，每个连接（包括每一跳重定向）都经过它。reqwest 对字面 IP 不调用解析器，因此重定向钩子另外检查每一跳的字面地址与协议。
- 地址策略与各操作自己的规则分开，后者保持不变：
  - WebDAV：同源重定向、拒绝 303、认证头；
  - 图片：禁止降级、Referer 只留源；
  - feed：重定向次数上限。
- 体积上限保持不变；每个请求一个总时限，涵盖解析、全部重定向与读正文，不因逐跳重建客户端而重置。
- 原生的出站集成测试扩展到四条请求路径各自的 `PublicOnly` 行为。

策略文件（决定 Q3）：
- 文件是数据目录里的 `outbound.json`。
- 只有确实“不存在”（`NotFound`）才是 `Unrestricted`；无权读取、格式错误、不是普通文件等一律在发出任何网络请求之前报错退出，不放宽。
- 服务器启动时，在任何出站工作之前，若文件不存在就原子写入默认策略（只允许公网、无放行）。
- 信任模型：只有数据目录的所有者（服务器的运行用户）写这个文件。CLI 必须以同一用户运行（文档给出 `docker exec -u` 等写法）；以其他用户运行时读不到文件，按上一条报错。
- 策略文件不属于配置导入导出的内容。资料库备份不含它，恢复后需先重新放置，再运行 CLI。

`/feed-proxy` 随 C4 删除。C1 改动共享的 infra，提交前同时跑 wasm 检查。

### C2 认证（`auth.sqlite3`）

认证数据单独存放在数据目录的 `auth.sqlite3`，不在资料库里，资料库备份不包含它：
- 所有者凭据：Argon2 哈希，以及“凭据代数”（每次改密码加一）；
- 会话：不透明令牌，库里只存摘要，带创建、最后使用、到期时间与创建时的凭据代数；
- CSRF 令牌：与会话绑定。

凭据初始化与旧部署迁移（决定 Q1）：
- `auth.sqlite3` 不存在时，按顺序取第一个可用的凭据建立它：
  1. `RSS_READER_WEB_PASSWORD_HASH`；
  2. `RSS_READER_WEB_PASSWORD`；
  3. 旧认证状态文件（`RSS_READER_WEB_AUTH_STATE_FILE`，或其默认路径）里的哈希。
- 建立成功后以库为准，环境变量与旧文件不再读取；旧的 HMAC 会话一律失效，升级后需重新登录一次。
- 旧部署因此不改环境变量也能升级。部署文档写明：新数据卷建立成功之前，旧认证卷保持挂载。
- 改密码用 `rssr-web passwd`，从标准输入读入。

会话（决定 Q4）：
- 对用户不可见：登录后浏览器自动记住，使用时自动续期，不提供设备或会话列表。
- Cookie 带 `Secure`、`HttpOnly`、`SameSite=Lax`，`Max-Age` 设为绝对上限（登录起 180 天），浏览器因此一直保留到绝对上限。“30 天未使用即失效”由服务器按最后使用时间判断。
- 最后使用时间最多每小时更新一次，避免每个请求都写库。
- 原子性：
  - 续期只更新已有的会话行，不会重建已吊销的会话。
  - 改密码在一个事务里递增凭据代数并删除全部会话。
  - 登录在写入新会话的同一事务里核对凭据代数：并发的改密码完成后，用旧密码通过校验的登录不会留下有效会话。
- 退出登录吊销本会话。改密码吊销全部会话。`rssr-web sessions revoke-all` 只吊销会话、保留凭据，供恢复备份时使用。

请求校验：
- 信任的公开来源由配置给出：`RSS_READER_WEB_PUBLIC_ORIGIN`，生产环境必填，开发环境可省略并按回环地址放行。反向代理之后，服务器内部的 HTTP 监听地址不是这个来源。
- 写请求的 `Origin` 必须与公开来源完全一致；缺少 `Origin` 或为 `null` 时拒绝。
- 登录前：登录表单同样要求 `Origin` 一致，并保留失败限速。
- 登录后：页面经 `GET /api/v1/session` 取得与会话绑定的 CSRF 令牌，每个写请求在 `X-RSSR-CSRF` 请求头里带上。退出登录是带同样校验的 `POST`。
- 未登录访问 `/api` 返回 JSON 401；`/api` 不落入 SPA 回退。
- 验收经由真实的反向代理配置进行（登录、退出、每个写路由）。

冒烟辅助路由 `/__codex/*` 删除，冒烟改由测试代码自行搭建；`run_rssr_web_browser_feed_smoke.sh` 在同一提交里改写或退役，其覆盖的语义先迁入新的测试。

### C3 API（`/api/v1`）与后台任务

路由：
- 24 个操作各对应一个路由。请求与结果直接用 application 的公开类型（JSON）；错误体为 `{ code, message, request_id }`。路由、协议版本与错误体定义在 `rssr-api`，服务器与客户端共用。
- 按实际副作用区分读写：读用 `GET`；有副作用的用 `POST` / `PUT` / `DELETE`，包括 WebDAV 拉取与阅读页图片本地化。
- `ensure_auto_refresh_started` 不是路由：`HttpBackend` 里是空操作，服务器启动时开始唯一的定时刷新（C5）。

后台任务（决定 Q2）：
- 五个操作走后台任务：刷新全部、刷新单个订阅、添加订阅（含首次刷新）、WebDAV 上传、WebDAV 下载。其余 19 个操作一次请求完成，包括配置 JSON 与 OPML 导入（单次事务、有大小上限）和阅读页图片本地化（带时限）。
- 状态：排队 → 运行 → 成功 / 失败。任务状态与业务结果分开：失败的任务也可能已有部分订阅提交成功。
- 准入在任何副作用之前进行：容量已满时直接拒绝，返回“服务器忙”。名额一直占到执行结束，与是否有人轮询无关。
- 任务 id 为 128 位随机值，重启前后不会撞号。发起请求的客户端断开后任务照常执行。
- 结果从完成时起保留 10 分钟，结果总大小有上限。轮询可以等待一段有限时间，最长 10 秒。
- 重启后或保留期过后，轮询明确返回“状态不可用”。

结果未知：
- `ErrorCode` 新增“结果未知”。`HttpBackend` 在写请求已经发出、却没有收到回包时（断线、超时、连接被重置）返回它；没有拿到任务 id 的任务创建同样如此。
- 界面运行时统一处理，与后端无关：显示“结果未知”，然后重新读取受影响的状态。重新读取的结果不当作这次命令成败的证明，不显示为“已成功”。
- 写请求一律不自动重发，包括 WebDAV 下载这类会替换本地配置的操作。只读的轮询可以按退避重试。

上限，与批量已读语义协调：
- 列表查询有条数上限。
- 批量已读的预览先计数，目标集合超过上限（暂定 10 000 篇）时直接拒绝，并提示缩小筛选范围；不截断、不分批，保持“完整集合比较、一次提交”。确认请求的体积上限按预览上限设定。
- 配置 JSON 与 OPML 导入、请求体、并发都有上限。

版本：
- 服务器与网页包在构建时嵌入同一个构建标识：发布构建用发布 tag，开发构建用 `dev-<提交>`；不用 `CARGO_PKG_VERSION`，它长期停在 0.1.0。
- 每个请求带 `X-RSSR-Build`。缺失或不一致时，服务器拒绝一切写请求（含任务创建），读请求照常；页面提示重新加载，并保留正在编辑的内容（设置草稿、CSS）。
- 验收用两个不同构建标识的包实测。

### C4 网页端改用服务器（`HttpBackend`）

- `rssr-app` 新增 `HttpBackend`。正式 Web 构建启动时选它；演示站构建（`pages-demo`）在阶段 D 之前继续使用浏览器存储。页面代码不区分两种后端。
- 正式 Web 构建删除浏览器存储后端、本地浏览器门禁（`localStorage` 里的本地口令）与 `/feed-proxy` 回退。
- 依赖图门禁继续保证正式 Web 不含 SQLite；另加检查，证明正式 Web 确实选用了 `HttpBackend`、没有链接浏览器存储，演示站构建另外验证。
- CI 的 `feed-proxy-isolation` 任务在同一提交里退役，其语义（不代抓内网、隔离上游文档）先由 C1 的策略测试覆盖。
- 自动刷新由服务器负责。其他设备的修改，在页面聚焦、任务完成或重新连接后重新读取。

### C5 服务器运行与维护

- `rssr-web` 打开数据目录（`--data-dir` / `RSSR_DATA_DIR`，容器内 `/data`）里的 `library.sqlite3`，经 `LocalBackend` 调用用例。服务器端的 host 与原生相同（含图片本地化），出站策略来自 `outbound.json`。
- 唯一的定时刷新任务，不依赖浏览器在线：
  - 设置的重新读取与刷新间隔分开，至多每 60 秒重读一次。间隔改短（例如 CLI 把一年改成一分钟）后，至多一分钟就生效。
  - 用受控时钟测试“长间隔改短”。
- 备份：
  - infra 提供一个在事务之外运行的维护操作：`VACUUM INTO` 写到目标目录里新建的临时文件，成功后改名为目标文件。
  - 目标已存在时拒绝；失败时删除临时文件。
  - 入口为 `rssr-cli backup <文件>`，单独占一个提交。
- 恢复（写入部署文档）：
  1. 停止服务器与所有 CLI，确认没有进程打开资料库。
  2. 把旧的 `library.sqlite3` 与 `-wal`、`-shm` 一起移走，再放入备份。
  3. 重新放置 `outbound.json`。
  4. 两条路：
     - 已有 `auth.sqlite3`：运行 `rssr-web sessions revoke-all`，保留凭据、吊销全部会话；
     - 新主机、没有 `auth.sqlite3`：按 Q1 的顺序有意地提供当前凭据。
  5. 启动服务器。

### C6 部署与迁移

- Compose 与部署文档改为数据卷 `/data`，内含 `library.sqlite3`、`auth.sqlite3` 与 `outbound.json`；新数据卷建立成功之前，旧认证卷保持挂载。
- 从旧版 Web 升级：架构已确定断代，只能在旧版页面导出配置 JSON，升级后导入；文章不迁移。

## 提交顺序与验收

每一步单独验证，并送独立评审：

1. **C1 出站策略。** 地址判定用例；四条请求路径的 `PublicOnly` 集成测试；策略文件的各种失败；wasm 检查。
2. **C2 认证。** 会话的第 29 / 30 / 180 天用受控时钟测试；重启后会话仍有效；退出与续期并发；登录与改密码并发；CSRF / Origin 拒绝；401 JSON；登录限速；旧凭据迁移。冒烟脚本同一提交改写。
3. **C3 与 C5 的服务器部分。** 用原始 HTTP 请求对每个路由做契约测试，与独立的 `LocalBackend` 夹具对照结果；任务的准入、名额、保留期、重启与 id；结果未知；批量已读上限；构建标识不一致；定时刷新重读设置。
4. **C5 的备份。** 并发写入时 `VACUUM INTO` 得到一致副本；目标已存在时拒绝；中途失败清理临时文件。恢复流程按文档实操一遍。
5. **C4 网页端切换。** 特征测试；wasm 检查；依赖图门禁；正式 Web 与演示站分别验证；退役 `feed-proxy-isolation`。
6. **C6 文档与 Compose。**

阶段门禁（架构文档）：
- 两个浏览器加 CLI 共用一个资料库，含服务器与 CLI 的写入竞争及运行用户；
- 提交后断线与重试；
- 配置指纹冲突；
- 重启；
- 备份与恢复；
- 认证、CSRF、SSRF；
- 真实界面验收，经由反向代理；
- 独立评审。

## 已确认的决定（Develata，2026-10-15）

- **Q1 所有者凭据**：首次启动时由现有配置建立凭据（顺序见 C2，含旧认证状态文件），此后以 `auth.sqlite3` 为准；改密码用 `rssr-web passwd`。旧部署升级时不用改环境变量。
- **Q2 后台任务**：刷新全部、刷新单个订阅、添加订阅（含首次刷新）、WebDAV 上传与下载走后台任务；配置 JSON 与 OPML 导入同步执行；阅读页的图片本地化同步执行、带时限。
- **Q3 CLI 的出站策略**：由数据目录里的 `outbound.json` 决定。存在时服务器与 CLI 都执行 `PublicOnly`，确实不存在时为 `Unrestricted`，读取失败时报错、不放宽（见 C1）。
- **Q4 会话**：不做设备记录与会话面板（与功能设计哲学不符）。登录后由持久 cookie 自动记住，使用时自动续期；30 天未使用过期，另有 180 天的绝对上限。退出登录吊销本会话，改密码吊销全部会话，都不需要界面。通行密钥（WebAuthn）暂不做，以后可以加，不改变会话设计。
