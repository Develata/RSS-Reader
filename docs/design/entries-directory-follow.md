# 文章列表目录：手动浏览与自动跟随

确认日期：2026-10-03。状态：已按授权在 draft PR19 实施；验证结果和限制见[交接记录](../handoffs/2026-10-03-directory-follow-rust.md)。

## 范围与目的

这里讨论文章列表页的左侧主文章列表与右侧分组目录，不是单篇文章正文的标题目录。用户可能独立滚动目录，寻找很久以前的文章；重新滚动主文章列表时，则希望目录回到列表当前位置，减少无关信息。

本设计遵循[功能设计哲学](./functional-design-philosophy.md)与 [UI 分层边界](./ui-shell-bus-page-facade.md)，入口见[设计文档索引](./README.md)。

## 已确认的完整交互规则

1. 用户在右侧目录内部滚动，或操作目录组的展开/收起时，进入目录手动浏览。目录可以独立于左侧列表位置浏览旧文章。
2. 手动浏览期间，用户可任意展开或收起任何组，包括左侧列表当前位置对应的当前组。自动展开、自动对齐或重新定位不得打断这一过程；当前组并非始终不可折叠。
3. 用户一旦在目录外滚动左侧主文章列表，目录即恢复自动跟随，并跳转/对齐到主列表的当前位置。即使仍在同一个组内，也必须恢复；不等待跨组或换章节，不要求用户操作跟随开关。
4. 恢复跟随时，重置此前手动展开状态，收起其他组，只展开主列表当前位置对应的目录路径（包括显示该位置所必需的祖先组）。不合并或保留此前手动打开的无关组。
5. 自动跟随期间，目录随主列表当前位置更新，并保持仅展开当前位置路径；用户再次在目录内滚动或展开/收起，重新进入手动浏览。
6. 上述规则按用户操作来源区分，鼠标与键盘必须保持相同语义。内部模式是实现概念，不是新增的用户设置或切换开关。

“目录外滚动”表达用户回到主文章列表的意图，不能直接等同于任意 DOM 滚动事件。程序化滚动、事件冒泡、嵌套滚动及惯性按下述来源契约处理；平台待验项不能削弱第 3 条。

## 用户原意依据

> 当前组当然不是始终展开，如果是在目录里面滚动，那么可以任意展开/收起，不会被自动展开；但是，如果目录外的界面只要发送了滚动，那么右侧就会被自动跳转到当前位置（设计思路是这样的：如果我想要找很久以前的文章，会滚动目录，而不在意左侧主文章展示页；而如果我在滚动左侧的所有文章列表，那么我不需要再保留右侧目录的状态，我会倾向于它能跟随我的意识，与左边的所有文章列表同步）

针对恢复跟随时是否重置其他组，用户进一步确认：

> 那我觉得应该重置其它组，这样更干净，而且信息量更少了，因此如果能设计好的话，性能与内存占用能更好一些

## 实现方向与边界

用户已选择直接统一 Rust 目录状态并一起修复，不先实施独立的 JS 事件拦截小修。最初文档任务未实施；后续已授权在 draft PR19 中实现与验证。

- Rust 统一管理目录交互状态及状态转换，手机顶部目录和桌面右侧目录共享状态，各消费者独立订阅所需部分。
- 目录交互状态不进入文章 presenter，不让目录滚动或展开变化引发无关文章投影重算。
- JS 可保留必要的 DOM 测量和滚动能力；避免每帧通过 IPC 传递全量目录状态。
- 这属于前端内部状态职责收敛；application / domain 的文章、分组及用例语义保持统一。平台事件、测量与滚动差异限制在 adapter / host capability 边界，不回流为业务层的平台分支，也不要求存储或后端迁移。

## 性能与内存目标

性能不退化、减少内存占用是目标。收起其他组首先降低可见信息量，不能据此宣称已降低内存。测量应使用同宿主 release A/A 重复以及交替 A/B、B/A，保留原始样本与构建来源；不得把 Chrome 与 WebView2 的绝对耗时直接比较。

本次保留折叠 DOM。CSS 折叠不保证减少内存；若后续考虑卸载节点，必须验证首次展开、恢复自动跟随及连续滚动均不卡顿，并评估重建成本、焦点与滚动稳定性。DOM 条件加两次 rAF 只是代理时延，不代表真实显示时延或掉帧率；Wasm 线性内存容量也不等于存活对象占用。

## 2026-10-03 实施方案

- 页面内 Rust 状态分别保存初始化路径、实时观测路径、跟随模式与手动展开集合。跟随时仅当前组展开；进入手动时以当下展开状态为起点，按钮提交按已呈现 DOM 得出的明确开/关意图，避免异步观测先到 Rust 后再次反转按钮意图。
- 顶部目录和右侧目录分别订阅状态并复用既有 presenter 的 `Arc`，不复制全树，不把目录状态加入 `EntriesPresenterInput`。
- DOM adapter 将用户输入来源与实际滚动目标关联：目录输入进入手动；新的目录外滚轮、滚动键、触摸或滚动条操作引起主列表实际滚动，才恢复跟随。内部嵌套控件独立滚动不算主列表滚动；目录边缘滚动链仍归目录手势，直到出现新的主列表输入。
- 导航显式请求目标并等待目标页 DOM；它更新活动位置，但同页导航不抹去手动浏览。新分页/分组/查询上下文重建目录状态；程序化对齐及导航均不伪装成用户主列表滚动。
- 观测按变化发送；同一 bridge 单条在途，其余观测/显式意图按键合并并保留最新顺序，积压由当前目录组数约束。上下文代际隔离旧消息，卸载显式关闭 bridge 与监听。
- 对齐命令携带状态版本；adapter 经 DOM 变更观察确认所有已挂载消费者完成该版本渲染后才测量与对齐，不将一次 rAF 当提交保证。按键不触发同步全目录布局扫描。
- 暂保留折叠 DOM，先验证同宿主 release A/A 和交替 A/B，再讨论节点卸载或其他性能架构。

## 来源契约与仍需验证的边界

- 事件来源：新的可信滚轮、滚动键、触摸或滚动条输入，加主列表实际位移，构成恢复跟随；单独程序化滚动仅更新活动位置。目录自身对齐不会恢复跟随。
- 冒泡与嵌套：目录输入按最近来源归属，即使冒泡或到边缘带动外层，也保持手动。嵌套控件自身位移不恢复；嵌套到外层滚动链的跨平台细节仍需真机补验。
- 惯性与并发：以最新输入来源优先，主列表归属在 1500ms 内的实际连续滚动中续期；目录新输入覆盖此前主列表惯性。迟到滚动不单独产生新意图。触控板、触屏、拖动滚动条及长停顿惯性仍需分别实测。
- 键盘：目录按钮的鼠标、Enter、Space 提交相同的明确开/关意图；目录内滚动键进入手动，主列表滚动键须产生实际位移才恢复。输入控件、修饰键与按钮 Space 激活不冒充主列表滚动。辅助技术尚无实机验收。
- 目录导航：同页跳转保持手动；跨页等到目标上下文与实际 DOM 就绪再跳转。新分页/分组/查询上下文重建状态；旧上下文导航和排队消息不能串入新上下文。畸形既有 hash 不阻断导航。
- 定位与生命周期：沿用距视口顶部 96px 的锚点规则，桌面仅滚目录容器，顶部仅横向对齐。版本确认覆盖已挂载的隐藏消费者；离开页面显式清理，返回时只有一个 tracker。
- 跨端消费：Web 的 360/720/721/1280 宽度与 Windows WebView2 专项分别验证。响应式模拟不等于 Android 原生或真实触摸测试。

这些是实施层问题；任意折叠当前组、主列表同组滚动即可恢复跟随、恢复时重置其他组等产品规则已经确认。

## 历史证据与后续验收契约

[2026-04-14 分页交接](../handoffs/2026-04-14-entries-page-pagination.md)记录过“激活强制展开”、常驻 DOM 等历史方案；它保留当时的实现与验证事实，不是本设计的现行约束。

最初仅文档阶段位于 main，未取用 PR19 分支。后续实施获授权后，安全转到 PR19 分支并读取其[历史基线](../testing/directory-regression-baseline.md)：旧“活动组不可折叠”契约的四个键盘失败及原始 JSON/CSV 原样保留。该历史记录不能反过来否定本次明确的产品原意，也不能算作新契约通过的证据。

新契约以固定 fixture 目标、显式用户预期和真实位移断言验证事件来源及鼠标/键盘一致性，不从运行时活动组推导预期，不跳过失败场景。还用同一新契约反测旧产物。下表为验收规则，执行结果单列于交接记录：

| 场景 | 最新预期 |
| --- | --- |
| 在目录内滚动寻找旧文章 | 保持独立浏览，不自动对齐回左侧当前位置 |
| 用鼠标或键盘收起当前组、展开其他组 | 允许操作，不被自动展开覆盖 |
| 手动浏览后，在主列表当前组内滚动 | 立即恢复跟随并对齐，重置其他组，仅展开当前位置路径 |
| 主列表滚动跨组 | 跟随新位置，仅展开新路径 |
| 恢复跟随后再次在目录内浏览或折叠 | 再次允许独立操作，包括折叠当前组 |
| 程序化滚动、冒泡、嵌套或惯性事件 | 依据上述事件来源契约验证，无错误抢占或反馈循环；真机待验项单列 |

交互通过、性能通过和内存收益是分别举证的结论，不能彼此替代；本设计不构成合并或发布授权。
