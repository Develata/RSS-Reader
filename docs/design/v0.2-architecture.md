# v0.2 架构：服务器端 Web、统一 SQLite 存储与 Pages 演示（已确认设计，实施中）

- 决定日期：2026-10-13（Develata 确认）
- 设计过程：Claude 与 Codex（gpt-6-astra，max）各自独立设计后讨论四轮收敛；讨论原文不入库，结论以本文为准。
- 发布：完成下文阶段 A–D 后统一发布 `v0.2.0`。这是断代版本，见“兼容性”。

## 目标

1. **正式 Web 是自托管的服务器端阅读器。** 数据保存在所有者自己的服务器上；任何设备登录后获得与桌面 GUI 相同的完整功能，所有设备看到同一份资料库。单一所有者，部署在 HTTPS 之后。服务器上的 CLI 与 Web 共用同一数据目录，便于 agent 使用。
2. **GitHub Pages 演示站**：纯静态，在浏览器里用内存 SQLite 运行同一套应用逻辑与仓储代码，载入小型合成样例；不保存访客操作，刷新即重置；网络功能禁用。
3. **所有平台只有一套存储实现**：桌面、Android、CLI、服务器与演示站共用同一份 SQL、迁移与仓储代码（rusqlite）。

GUI 与 CLI 仍是两个程序，见 [GUI 与 CLI 的分发形式](./cli-gui-distribution.md)。

## 架构

| 组成 | 职责与依赖 |
|---|---|
| `rssr-domain` | 领域模型与端口；不依赖存储、HTTP、UI |
| `rssr-application` | 唯一的用例语义；定义**唯一一套**面向调用者的输入 / 结果类型（可序列化）；聚合查询端口保证读快照 |
| `rssr-api` | 薄协议 crate：后端接口、路由、协议版本、错误体、后台任务外壳；数据类型直接引用 application 的公开类型，不另建平行 DTO |
| `rssr-infra` | 同步 SQL 仓储核心、执行器（原生 / wasm）、迁移器、旧库导入器、出站访问策略、共享 host composition、`LocalBackend` |
| `rssr-app` | Dioxus UI；启动时选择一次 `LocalBackend` 或 `HttpBackend`；设备状态与客户端能力（剪贴板、打开链接、文件选择、时区）留在这里 |
| `rssr-cli` | 与 GUI / 服务器共用 application + infra 与同一数据目录 |
| `rssr-web` | axum：`/api/v1`、认证、内存后台任务、服务器定时刷新；不依赖 `rssr-app` |

- 桌面、Android、演示站走 `LocalBackend`（本机直接调用用例）；正式 Web 走 `HttpBackend`（HTTP 调服务器上的同一套用例）。页面代码不区分两者。
- 公开类型的边界：执行策略与内部数据不对外（例如刷新并发数、刷新结果中的本地化任务、原始 SQL 错误文本）；这类情况由 application 提供专门的公开输入 / 结果，而不是在 API 层另造一套。
- 文章列表偏好（分组、显示归档、已读 / 收藏筛选、选中的订阅）与“上次打开的订阅”属于资料库，随资料库在所有设备间共享：单一所有者，换设备时偏好跟着走（2026-10-14 Develata 决定，取代原先“保存在设备上”的设计）。滚动位置等纯界面状态留在设备。启动目标由一份规则结合资料库状态判断，不在客户端与服务器各写一份。
- 设置修改使用专门的“修改输入”，在一个事务内合并后统一校验；完整 `UserSettings` 不当作修改请求。
- 时间字段在协议中固定为 RFC3339，公开计数使用固定宽度整数而非 `usize`；`UserSettings` 同时决定数据库 JSON 与配置导出格式，修改其字段需单独审查磁盘与导出文件的兼容规则。

## 存储

原生资料库关闭时先停止接收全部读写任务，等待读连接退出，再关闭写连接。这个顺序让同一 store 的连接不在最终 WAL 检查点与清理时互相争锁；相关远端失败、复现与修复验证见 [C4c 远端 CI 记录](../handoffs/2026-10-22-c4c-remote-ci.md)。

- 一个库文件 `library.sqlite3`：索引、正文、设置、`generation`、刷新序号 `I/P/D`。正文仍是独立的表，列表查询不读正文列。
- 全新的基线 schema；迁移器统一按 LF 计算校验和，迁移与历史记录同一事务提交；拒绝未知版本与内容被改动的迁移。审计分支上未发布的迁移 0008（搜索用标题）、0009（自定义订阅名）直接并入基线：`title_search` 设为必填，删除只为兼容旧写入者而存在的触发器、部分索引与启动回填。
- 仓储核心是同步 SQL，返回自有数据：
  - 两端共同规则：每个任务一个事务，状态为 排队 → 运行 → 提交，或 → 取消。排队超过准入时限、或调用方离开时仍在排队的任务不会运行（工作线程在把任务标为运行之后再核对准入时限，晚于时限才轮到的任务直接取消）；运行中调用方离开则中断当前语句并回滚；“运行 → 提交”之后不再接受取消，提交照常进行但仍可能失败（例如等锁到期），调用方离开后不知道结果。取消的任务立即丢弃闭包及其捕获的数据，丢弃时的 panic 被隔离，不会终止工作线程。运行期限从任务开始计算：等待其他连接的锁到期限为止（busy handler），期限到时仍在执行的语句被中断（progress handler），两者都读取工作线程上的任务上下文；它们拦不住任务里的 Rust 代码，仓储任务必须由输入规模与库快照约束。期限到达时不在提交前拒绝，避免稍晚完成的刷新被反复判为失败。任务结束后连接恢复空闲状态，恢复失败的连接丢弃、下个任务重新打开。时钟只出现在执行器里（原生 `Instant`，wasm `Date.now()`；`std::time::Instant` 在 wasm32-unknown-unknown 上不可用）。
  - 原生执行器：每个连接由一个专属线程持有，任务经队列送达（1 个写线程、4 个读线程；内存库只有 1 个），不经过 tokio 的阻塞线程池。每个队列最多容纳 `queue_capacity`（默认 256）个尚未被工作线程取走的任务（含已取消的），等待空位计入准入时限。
  - 打开时把路径一次性转成绝对路径，身份探测、建库与所有连接都用这一个路径；连接不把路径当 URI 解释（`file:` 开头的名字仍是文件名），Unix 上反斜杠是文件名的一部分。
  - 新资料库（新建或从 v0.1 导入）由持有该路径“创建锁”的一方建立：锁是旁边 `library.sqlite3.create-lock` 上的咨询锁（`flock` / `LockFileEx`，进程退出即释放；锁文件保留不删）。持锁方从确认目标不存在到发布全程不放锁，在固定名字的暂存文件里建好（迁移完成、文件头已带应用 id、连接已关闭）后，用同目录 `rename` 原子发布；暂存文件只属于持锁方，开工前先清掉崩溃遗留（清不掉即失败），打开已确认身份的资料库时若无人持锁也顺带清理。因此正式路径上的文件要么不存在，要么是完整的资料库；并发的创建者排队等待（最多 120 秒，超时报错；调用方放弃后不再等锁，也不再开工），后到者看到目标已存在。这一保证只在遵守创建锁的程序之间成立：其他程序恰在检查与 `rename` 之间放到目标路径的文件不受保护。不依赖硬链接（Android 的 SELinux 策略不允许应用创建硬链接，FAT/exFAT 也不支持）。
  - 打开已有文件前，经 SQLite 以 `immutable=1` 只读方式读取应用 id 确认身份：不写入、不创建也不改动 `-wal`/`-shm`，也不会像单独打开再关闭文件描述符那样丢掉本进程其他连接持有的 POSIX 锁；应用 id 不符（包括空文件、文件头全零的外部库）一律拒绝。检查点按页号把日志写回主文件、第 1 页最先，进行到一半或进程在写回中途结束（崩溃、强杀、断电）时，第 1 页已记录更多页数而文件尚未增长；探测连接设 `writable_schema`，SQLite 便按文件实际长度读，照样读到应用 id（建库后不变，第 1 页新旧都带着它）。其余部分是否完好交给写连接：有日志时 SQLite 用它恢复，没有日志时写连接第一次读取即报损坏、拒绝打开（2026-10-21 起；此前探测把这种文件按损坏拒绝，共用数据目录的程序都打不开，直到有人用普通 SQLite 打开它）。探测只读第 1 页文件头（SQLite 读应用 id 前检查的字段新旧一致，超前的页数按上面读过去），撞上写入也无需重试；仍报损坏时按“数据库已损坏”拒绝打开；格式不是 SQLite 数据库的文件立即按“不是资料库”拒绝。
  - 关闭：程序退出前调用 `LibraryStore::close` 并等它返回（CLI 在每条命令之后，成功或失败都一样；`rssr-web` 正常停止时与结束运行同时进行，共用同一时限；桌面端在事件循环结束时；浏览器回归的夹具工具在写完之后）。已排队的任务照常执行，之后经任何句柄提交的任务得到“资料库已关闭”；每个连接都关闭后才返回，最后一个连接关闭时 SQLite 把日志写回主文件并删除日志。只丢弃句柄时，连接在无人等待的线程上关闭，进程恰在此时退出会让主文件停在写回中途，下次打开的身份探测按损坏拒绝（2026-10-20 夹具工具 60 次运行中出现 1 次）。Android 由系统结束进程，没有这个时机；进程被强杀、断电时同样可能停在写回中途，见交接记录 `2026-10-21-store-close-before-exit.md`。
  - wasm 执行器：连接保存在页面线程的 `thread_local` 里，仓储只持有一个索引句柄，因此是 `Send + Sync` 而不需要 `unsafe impl`。
  - 网络请求与解析不在数据库事务内进行。
- 配置替换与 OPML 导入只有原子路径：所需的原子端口是必要依赖，删除现有的逐步替换后备实现，测试也走同一契约。
- 保持现有查询语义：搜索仍是 `fold_for_search` + `instr`（Unicode 小写 + 字面子串），大范围筛选仍用 `json_each`。
- 驱动：原生 `rusqlite 0.40.2`（`libsqlite3-sys 0.38.2` 捆绑 SQLite 3.53.2，sqlx 已移除）；浏览器侧经 `sqlite-wasm-rs 0.5.x`（与 `wasm-bindgen 0.2.126` 相容；rusqlite 0.40 的 wasm 后端是默认特性 `ffi-sqlite-wasm-rs`，阶段 D 关闭默认特性后需显式开启）。原生与 wasm 分别记录实际 `sqlite_version()` 与 `sqlite_source_id()`，SQLite 基线不低于 3.51.3（WAL-reset 修复）。两端的引擎来自不同的 crate（原生 `libsqlite3-sys`，wasm `sqlite-wasm-rs`），版本各自升级，共享的 SQL 用例必须在两端都跑。
- 跨进程刷新协调：每个订阅持久化 `I`（已发出的最大序号）、`P`（已发布的最大序号）、`D`（已记录诊断的最大序号），始终 `0 ≤ P ≤ D ≤ I`。刷新开始时在写事务内领序号 `t`，同时读取要发送的校验器和它们所属的 `P`（基线）。提交时：
  - 200 只有 `t > P` 才发布（内容与校验器），`P := t`、`D := max(D, t)`；
  - 304 只有基线仍等于 `P` 才记录，`P := t`、`D := max(D, t)`；304 未重发的校验器取自这次请求发出的校验器（它们属于领号时的 `P`），不取自库中当前行（其间的失败可能写入了从未发布的响应的校验器）；
  - 失败只有 `t > D` 才记录（错误与抓取时间），`D := t`；
  - 抓取时间与错误属于最新的诊断：`t < D` 的发布（较新的失败之后到达的较旧成功）不改动它们；
  - 不满足条件的提交什么都不写，报告为被取代，界面显示为“未变化”（被取代的失败也是）；
  - 每次提交都必须带着它所回答的请求的序号（来自 `begin_refresh`，`get_target` 交出的目标同样领号；或来自订阅激活）；没有序号的提交被拒绝：提交时才领号会把较早的请求排到较新的之后，还会给旧的 304 凭空造出基线。

  添加订阅时的预抓取结果在激活事务内领序号；数据库事务（及其锁）都不跨网络请求，进程内每个订阅的互斥锁覆盖该订阅的抓取与提交（同进程内不重复抓取同一订阅）。每次刷新多一个领号的小写事务，领号必须在抓取开始时逐个进行，序号顺序才等于抓取开始顺序；实测每次约 1.7 毫秒（文件库、WAL、`synchronous=FULL`、Windows SSD、release）。进程内抓取序号只用于没有持久化序号的存储（浏览器存储），带序号的目标完全由存储判定。

## API（`/api/v1`）

- 按用户操作组织：启动数据、文章列表、阅读页快照、标记修改、批量已读的预览 / 提交、订阅列表、添加 / 删除订阅、刷新、设置修改、配置与 OPML 导入导出、远端配置。读结果在一个读事务内聚合。
- 标记传目标值（`is_read=true`），不做版本号；`read_at` / `starred_at` 只在状态真正变化时更新；批量已读在写事务内比较完整目标集合。
- 长操作：有界的内存后台任务，`202` + 轮询；服务器重启或结果过期时明确返回“状态不可用”；任务状态与业务提交结果分开（任务失败可能已有部分订阅提交）；保留部分成功与“订阅已保存、首次刷新失败”的区别。
- 破坏性操作（配置替换、OPML 导入、删除订阅、批量已读提交）：客户端不自动重试；回包丢失时显示“结果未知”并重新读取状态。配置替换必须携带读取时的配置指纹（规范化的订阅身份、地址、`generation`、自定义名称、分组与设置），服务器在同一写事务内比对，不一致就拒绝；指纹的计算与比对共用一份定义。
- 网页包与服务器同版本发布：版本不一致时服务器拒绝写入，页面提示重新加载，并保留正在编辑的内容（如 CSS 草稿）。
- 错误体 `{ code, message, request_id }`；内部原因只进日志。

## 安全与运行

- 认证单独存放在 `auth.sqlite3`：Argon2 所有者凭据、只存摘要的不透明会话令牌、会话绑定的 CSRF 令牌；改密码撤销全部会话。Cookie `Secure` + `HttpOnly` + `SameSite=Lax`；登出改为受保护的 POST；校验精确 Origin 与自定义请求头；未登录的 API 返回 JSON 401；`/api` 不落入 SPA 回退。
- 出站访问（抓 feed、发现订阅、图片、WebDAV）共用一套 infra 策略：服务器默认只允许公网地址，内网例外由管理员显式配置；同目录的 CLI 执行同一策略；桌面 / Android 保持允许访问内网的现状；演示站禁用网络。
- 请求体、导入大小、查询规模与并发都有上限。
- 服务器唯一的定时刷新任务，不依赖浏览器在线，并重新读取 CLI 可能改过的设置。
- 服务器与 CLI 共用 `--data-dir` / 环境变量指定的数据目录（容器内 `/data`）；资料库备份用 SQLite backup API 或 `VACUUM INTO`，不含认证文件；恢复时停止写入者并清空会话。
- 正式 Web 没有离线资料库，也不是实时同步：网络或服务器故障时无法阅读；其他设备的修改在页面重新读取（聚焦、任务完成、重连）后可见。

## 兼容性（断代）

- 不再支持：新旧版本同时运行、降级、旧浏览器标签页与旧浏览器存储格式。升级前须关闭所有使用同一数据目录的旧进程。
- 保留：桌面 / Android / CLI 的旧库单向导入。支持全部已发布的 v0.1.0–v0.1.23，按两种历史正文布局读取（v0.1.0–v0.1.6 正文在索引库内；v0.1.7 起为双库）；接受已知、完整提交的迁移前缀；持新资料库的创建锁取得包含已提交 WAL 数据的稳定副本（源库被占用超过 busy timeout 即失败），原文件保留；在暂存库中完成完整性与保真检查后才发布；`custom_title` 为空、逐条计算 `title_search`、初始化刷新序号，文档保留原 `updated_at`；v0.1.2–v0.1.6 的 `last_opened_feed_id` 与 v0.1.6 的列表偏好在没有应用状态时并入应用状态；缺正文库的双库布局只有在索引库没有记录任何正文时才导入；两种布局都只导入有 HTML 或文本的正文，源库的不一致（标记有正文却没有、正文挂在别的订阅下、空正文）计入导入报告；未发布的 0008 / 0009 开发库明确拒绝。旧库只从新资料库所在的数据目录本身查找（固定文件名；悬空链接或非普通文件报错，不当作没有旧库），共用数据目录的程序因此做出相同选择，前提是旧文件在任一新版首次启动前就位、且这些程序都经打开或导入入口打开；macOS 的 v0.1.x 数据在应用包内，由用户在升级前复制到新数据目录。
- 浏览器里的旧资料库只能通过配置导出 / 导入迁移订阅与设置，文章不迁移。

## 演示站

页面内的 `LocalBackend` + 单连接内存 SQLite，与其他平台共用 SQL 仓储；载入合成样例；不保存操作，刷新即重置；网络功能禁用；正式 Web 的构建不包含 SQLite 与样例。

每个阶段是一组独立、经过验证的提交，并送独立评审。

## 已知代价（决策时已接受）

- 自写的数据库执行器与迁移器是长期维护的基础设施，出错会影响全部存储。
- 服务器上的 CLI 直接读写数据库，服务器不是唯一协调者：它的任务列表与并发上限看不到 CLI 的工作；正确性依靠数据库事务，定时任务与页面需重新读取持久状态。
- 设备状态与资料库状态分两处保存；设备记住的位置可能因其他设备删除订阅而失效。
- 单个库文件：正文与标记写入争同一写锁，整库维护成本更大（原双库拆分是职责分离，未做过性能测量；表与查询边界保留）。
- 配置指纹是另一份“哪些配置会被替换”的模型，需集中定义并随替换范围审查。
- 用户会看到“结果未知”；服务器升级后打开的页面必须重新加载。
- 旧库导入器是只为兼容存在的代码，按明确的升级支持政策退役。
- 断代：浏览器里的旧文章无法迁移；不能无损降级。
- 演示站展示不了服务器、会话与网络失败等正式 Web 的行为。
- 浏览器侧依赖 `sqlite-wasm-rs`，版本与 `wasm-bindgen` 联动；两端 SQLite 版本不同步。
- 演示站的构建要把 SQLite C 源码编译到 wasm32，需要带 WebAssembly 后端的 clang 与 `llvm-ar`（Android NDK 自带的 clang 可用）；正式 Web 不含 SQLite，不受影响。
- **组合代价**：服务器化本身不要求替换 sqlx；“所有平台共用同一 SQLite 仓储”的目标让演示站影响了全部平台的存储选型。选择 rusqlite 另有两条独立理由：SQLite 修复不必等 sqlx 跟进（WAL-reset 修复曾需要整体升级 sqlx），以及能直接使用 SQLite 专用接口。

## 刻意不做

持久化的命令回执、持久化后台任务与自动续跑、标记版本号、强制使用 Worker / OPFS、正式 Web 的离线写入队列、跨设备副本合并、浏览器文章归档迁移、新旧程序共用一库与降级、旧网页包的长期兼容矩阵、换 ORM 或换数据库引擎、全文检索（FTS）。

## 备选方案

- Diesel：最有力的备选（同样支持浏览器 SQLite，依赖范围更宽）；未选，因为本项目的手写 SQL 与 SQLite 专用接口的适配成本更高。
- libSQL：其 wasm 接口访问远端 HTTP，不满足无服务器演示站的组合目标。
- Turso（原 Limbo）：换引擎，FTS 不兼容 SQLite，多进程 WAL 协调仍为实验性，缺少 backup / serialize / 自定义函数等接口。
- 直接使用 `sqlite-wasm-rs`：原生端仍要另接一套绑定，相当于重写 rusqlite 的一部分。
- Dioxus server functions：可以承载用例层 API，但会让协议依赖 UI 框架；选用显式的 axum API。
